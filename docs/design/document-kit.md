# Portable document kit design

<a id="d113"></a>

## 1. Contract-driven authoring

`XDesignDetailedDesign::DocumentContractEngine` is designed to take a
selected project root and a versioned profile. The profile lists document
classes, each class's relative path, required ordered chapters, anchor
policy, and template. Callers supply the stable section IDs. The same
contract data is intended to drive planning, writing, and checking;
agents should not maintain separate copies of naming or chapter rules.
The profile, `RULES.md`, and real Markdown templates are delivered together
under `document-kit/`. A consumer can version that directory with its
project and select its own profile. Content is supplied by the authoring
agent; a template must not invent requirements, design rationale, model
relationships, or test results.

## 2. Operations and invariants

| Operation | Result or invariant |
| --- | --- |
| Read contract | Return profile version, classes, required sections, template and rule text. |
| Plan document | Resolve one class and semantic slug to its permitted project-relative path and required section inputs before writing. |
| Create document | Render the selected template from caller-supplied content; validate required fields and the complete output before writing. Refuse an existing destination; updates use the separate section operation. |
| Update section | Locate one stable anchor and replace its section body while preserving other anchored sections; validate before commit. |
| Attach figure | Require an existing canonical model-derived SVG under the carrying page's `assets/` child and add its six-field block after the embed in the intended anchored section. |
| Check documents | Return structured rule codes and locations for path, chapter, content, locator, figure and embed failures, plus explicit review obligations. |

The model declares `ReadDocumentContract`, `PlanContractDocument`,
`CreateContractDocument`, `UpdateContractSection`,
`AttachContractFigure`, and `CheckContractDocuments` as the engine's
operations. `DocumentCliAdapter` and `DocumentMcpAdapter` each reference
the engine. Their planned source projection is:

| Model element | Source projection |
| --- | --- |
| `DocumentContractSource` | `document-kit/profile.json`, `RULES.md`, and `templates/` |
| `DocumentContractEngine` and six actions | `document-kit/xdesign_doc_kit/core.py` |
| `DocumentCliAdapter` | `document-kit/xdesign_doc_kit/__main__.py` |
| `DocumentMcpAdapter` | `document-kit/xdesign_doc_kit/mcp_server.py` |

The caller supplies structured metadata, section content, and figure fields;
the action's `callerContent` and report values denote those serialized
request/response payloads, not prose generated by the engine. The source
implementation must be checked against these allocations before an
implementation claim is made. The exact planned JSON operation, result, and
error contract is [I20](../interfaces/document-kit-api.md#i20).

Paths must remain inside the selected project root; traversal and symlink
escapes are errors. A write that fails validation leaves the existing document
unchanged. An update or figure attachment requires the expected document
SHA-256 and refuses stale content. Repeating the same request must not
silently create a duplicate section or figure. The CLI and MCP adapter must call
the same operations and return equivalent findings. MCP transport would make the
capability callable by different agents; it does not itself enforce a work
sequence. The portable skill directs agents to plan and write model-linked
documents before implementation, then to run checks and record separate
design review. A consumer flow or CI must bind the document checker as a
gate if it needs progression to be blocked on a failed document contract.

## 3. Check boundaries

Required headings, section IDs, nonempty caller-supplied content, unresolved
template slots, allowed paths and figure blocks are deterministic predicates.
The existing [xdesign documentation audit](../interfaces/documentation-contract.md#d31)
checks this repository's `DocSection` and `DocFigure` targets and local
embeds. A reusable profile may select equivalent checks for another project's
model layout. The pinned compiler separately checks SysML syntax and supported
references. No structural pass determines whether prose faithfully explains
the model, whether a figure answers its engineering question, or whether its
labels are readable at article width. Those remain review judgments backed by
the final document, model, and rendered asset.

## 4. Source allocation and scope

The versioned `document-kit/` pack owns the profile, rule explanation, five
Markdown document templates, figure-block template, and portable skill.
The source projection table assigns the Python engine, deterministic CLI,
stdio MCP adapter, and cross-project fixtures. The starter profile covers
five flat document classes; xdesign's flow-specific and per-API routes need
a reviewed derived profile before being generated. This design does not
change the main Rust application's stage CLI or the bundled SysML compiler. The
[portable architecture](../architecture/document-kit.md#b33) defines
ownership, and [DocumentKitVerification](../verification/design.md#d114)
defines the acceptance cases. Current implementation status, executed
results, and any limits belong to the wish and review records. Neither a
model annotation nor a passing documentation check establishes this
component's implementation or engineering acceptance.
