# 项目模型与 Wish SysML 详细设计

状态：目标详细设计草案。日期：2026-10-13。依据：[架构设计](../arch_design.md)。本文定义项目工程模型、每条 wish 的独立模型和原生 view 的契约，不规定用户仓库必须采用的目录，也不声明现有模型已经产生实际成果。

## 1. 职责与共同对象

ProjectModel 表达被开发系统的组成、接口和行为。WishModel 解释一条 wish 怎样落实为需求、设计、实现、验证和交付依据。NativeView 从这些原生模型中选择要展示的内容。它们都是持续演进的工程资产，项目接入时固定的是工具处理机制。

本设计采用 [overview.md](overview.md) 的共同对象：ProjectModel、WishModel、NativeView、WorkflowProfile、ConstraintSet、Candidate、Attempt、CheckResult、Decision 和 ReleaseAssociation。这些是逻辑契约，不要求每个对象独占一个新文件或数据表。

流程与阶段职责由 [v_model_sysml.md](v_model_sysml.md) 定义；关系和历史由 [trace.md](trace.md) 定义；关卡由 [gate.md](gate.md) 定义。本文负责原生模型应该包含什么、哪些内容共享，以及应用怎样核对模型提交。

## 2. 模型层次与维护来源

| 内容 | 维护职责 | 项目中的变化方式 |
| --- | --- | --- |
| 工具公共元模型与流程定义 | 工具提供元素类型、关系含义、解释和渲染机制 | 采用项目绑定的工具版本，不随工程编辑变化 |
| ProjectModel | 工程人员维护真实系统的部件、接口、行为及关联 | 开发中新增、修改，已有系统范围可逐步接入 |
| WishModel | 维护某条 wish 的工程解释、关系和完成范围 | 每条 wish 独立保存，持续补充各阶段内容 |
| ConstraintSet 与 WorkflowProfile 的工程 SysML | 用户维护阶段规范、规则选择和参与分配 | 可演进；尝试和决定引用实际采用的版本 |
| NativeView | 模型作者维护展示选择及所需关系 | 随所服务的工程模型改变；发布选择保留确定版本 |
| 事实引用节点 | 在原生模型中定位实际记录、证据与决定 | 引用原记录，不复制成第二份可修改事实 |

模型源保存在项目配置的工程位置并使用项目自己的版本管理。SysML 工具返回的解析表示、图索引和临时 HTML 不是模型的唯一来源。模型、文档和代码进入工程资料后的保存与持久化见 [storage.md](storage.md)。

## 3. ProjectModel 的原生契约

ProjectModel 至少具有可定位的模型入口、系统范围和原生组成关系。部件通过实际 `part` usage 表达；接口、端口、行为及责任使用适合的原生元素与关系。只导入文件或列出“客户端、同步、存储”等名称，不等于已经建立系统组成。

模型可以引用项目既有 SysML 元素，不要求重建整个系统。当前接入范围、未知部分和需要补充的关系须在模型及评审中可见。用户逐步接入已有项目不意味着历史实现已经通过当前 workflow。

### 3.1 身份与共享部件

每个被引用的工程元素必须能在版本选择中确定身份、所属模型和实际内容。限定名与源位置用于显示和解析；重命名、文件移动或重新解析不能默默把同一个部件变成一个新部件。稳定身份与语言元素的绑定方式遵循 [trace.md](trace.md) 和 [storage.md](storage.md)。

共享部件只有一个工程内容维护来源。多个 WishModel 引用同一个实际部件 usage，而不是在各 wish 文件中复制出可分别修改的客户端或存储部件。一个 `part def` 可以有多个实际 usage；同一个类型不意味着它们是同一个部件，应用不能按显示名称或类型名称合并身份。

共享内容允许分文件维护，归属通过原生引用确定。项目模型可以组合这些内容；目录、文件名和 import 关系不代替系统的组成关系。

### 3.2 实现与外部资料

代码、设计文档、构建产物和外部规范可以是模型元素引用的工程材料。引用至少能够确定材料身份、采用的内容版本以及所支持的工程范围；需要时定位到相关章节、代码单元或具体验证输出。

代码引用只能说明关联到了确定实现，不能仅凭路径推断设计已经被正确实现。原生需求满足关系也是一个待证据支持的工程主张，工程充分性由相应 AGENT 判断。

## 4. 每条 WishModel 的独立契约

### 4.1 独立保存和入口

每条 wish 至少有一个独立保存、可单独定位的原生 SysML 源入口，具有独立身份、命名空间和追溯 view。入口可以引用该 wish 的其他源文件及共享项目元素，不要求采用固定的文件命名或目录树。

不同 wish 可以共享需求、设计或证据，但各自必须能解释自己的范围和完成依据。全项目只有一份外部 ID 表或一张中心图片，不能代替每条 wish 的独立原生模型。

### 4.2 原始意图与工程解释

| 内容 | 模型必须能表达的含义 |
| --- | --- |
| 原始来源引用 | 用户何时提出了什么 wish，谁是来源或拥有者，如何定位原始内容 |
| Wish 工程入口 | wish 身份、工程解释、预期结果、使用范围及尚未确认的问题 |
| 需求入口 | 由意图形成的需要与要求，以及适用的验收意图 |
| 系统关联 | 涉及 ProjectModel 中哪些具体部件、接口和行为 |
| 实现与验证入口 | 哪些确定实现、验证计划和实际结果参与这条链 |
| 判断与交付入口 | 哪些关卡及完成判断依据，以及涉及哪个既有实际发布及关联 |

原始提交由事实记录保留；模型中的工程解释是可修改的工程内容。改变解释或 wish 本身时保存新版本并说明变化，不回写用户原来提出的内容，也不替用户补出未经判断的验收结论。

初始 WishModel 可以不具备所有后续成果，但必须显式显示尚未建立的工程范围。链的存在、完整性和 wish 已满足是不同结论；不能在创建文件时就填入完成或通过事实。

### 4.3 从意图到交付的原生链

WishModel 的追溯图应能连接以下工程角色：

1. wish 来源和工程意图。
2. 需要、系统需求与适用约束。
3. 具体部件、接口和行为设计。
4. 实际实现的确定引用。
5. 计划验证与使用确认。
6. 实际执行、观察和证据引用。
7. 关卡及完成 Decision。
8. 既有实际发布和 ReleaseAssociation 引用。

这不是要求把所有对象排成单一串联列表。多条需求可以分支，共享一个设计；验证与设计、需求之间使用相应原生关系。应用自定义 dependency 角色必须声明含义，不能把显示标签当作 `satisfy` 或 `verify` 的标准语义。关系类型、方向和历史选择由 [trace.md](trace.md) 统一定义。

外部记录通过类型化原生引用节点和关系参与链，节点指向原记录的确定身份和版本。它不能只是一条任意 source/target 字符串，也不能复制记录正文后产生另一套可独立修改的审批状态。

## 5. NativeView 契约

### 5.1 每份工程 SysML 的 view

每份用户项目维护的工程 SysML 都有相应原生 view，包括项目模型、独立 wish 模型、用户约束和 workflow 配置模型。工具附带的语言标准库和接入的第三方源文件不要求用户为此改写。

推荐把 view usage 与所服务的模型入口保存在同一源文件；通用 view definition 可由工具定义库复用。应用按项目配置识别 view 的归属，不通过不断创建“view 的 view”解决文件配对。

| 模型 | view 必须能够选择的核心内容 |
| --- | --- |
| 项目组成模型 | 系统范围、具体部件及其必要组成／接口／行为关系 |
| 独立 wish 模型 | wish 入口、需求、所涉及的设计、实现与验证、证据及决定引用 |
| 用户约束模型 | 规则的适用范围、阶段对象和规范引用 |
| workflow 配置模型 | 固定流程引用、本次范围、主体分配和阶段规则选择 |

模型作者可以补充不同关注点的 view。独立 wish 的追溯 view 至少覆盖该 wish 从提出到当前工程状态的完整上下文；内容过大时允许分层或按阶段查看，但不能只展示节点数或文件清单而隐藏决定依据。

### 5.2 编译与渲染核对

应用通过项目固定的 SysML 工具核对 view 是原生 view usage、引用对象存在、所需共享对象和关系被选择，并能够确定采用的源版本。导入共享模型不等于 view 已自动暴露其全部元素；相关共享元素和关系应被明确选入。

渲染图片、HTML 和查询结果是 view 的展示，不代替 view 声明。若当前工具不支持某种合法选择或不能渲染所需关系，应报告具体限制；不能以另画一张非原生图片声称原生 view 已满足。

查看当前开发内容、历史 Candidate 或发布关联时，应用明确选择相应版本的模型、view 和记录。打开旧关联不能解析到开发区最新决定，再把它显示为旧发布原有的判断。

## 6. 阶段怎样补充模型

下表给出固定阶段对应的模型内容。阶段规则可细化形式和数量；结构核对与工程判断分别记录。

| 阶段 | 应建立或核对的工程内容 |
| --- | --- |
| 利益相关方需求 | wish 来源、使用场景、需要、系统范围和待确认验收意图 |
| 系统需求 | 原生需求及其意图关联、适用约束、系统验证计划 |
| 架构与详细设计 | 实际部件、接口、行为、设计主张及相应验证计划；引用共享身份 |
| 实现与构建 | 对实际实现和配置的确定引用，连接到设计与需求范围 |
| 组件、集成、系统验证 | 计划与实际执行分开，记录被检查的实现及依据版本，关联真实证据 |
| 使用确认 | 场景和验收意图、实际使用证据、剩余问题及判断依据 |
| 交付与运行移交 | 选定的完成范围、Decision 与既有实际发布关联，不虚构发布事实 |

可执行结构检查核对：可解析性、原生元素和引用合法性、身份无冲突、必需关系与 view、当前阶段提交内容。工程语义判断核对：意图是否理解正确、需求是否足够、设计与代码是否一致、证据能否支持完成。完整图形和编译成功都不能替代工程判断。

## 7. 一次模型工作如何落地

1. 用户提交 wish，应用保留原始来源并在配置位置建立独立 WishModel 入口及 view。
2. 应用在 ProjectModel 中定位相关部件。已有部件沿用身份，新增部件明确其工程归属。
3. 当前阶段的工作主体编辑原生工程内容及 view，并提交实际源文件和关系，不以说明文字代替已保存模型。
4. 应用把提交范围、ConstraintSet、共享元素和外部材料版本选为 Candidate，再编译和执行相应结构检查。
5. 关卡 AGENT 判断同一 Candidate 的工程充分性；应用记录事实引用，使 WishModel 能定位实际 CheckResult 和 Decision。
6. 后续阶段更新链。发布关联按 [release.md](release.md) 核对实际产品版本，不为 wish 另造发布编号。

先保存真实记录并取得确定引用，再在新模型版本加入对应的原生引用节点；尚未发生的结果显示未发生。事实保存成功而模型接入失败时，保留待接入状态并恢复模型操作，不重复执行原任务。后生成的检查和决定不会被倒插到已审 Candidate 内改变其内容标识。新增事实引用保留其所支持的原候选，引用自身的结构另行核对，不因接入事实而循环推翻原工程判断。持久化交接见 [trace.md](trace.md)。

模型内容变大时，按部件和 wish 组织源文件，阶段读取相关范围及依赖。已有完整工程资产保持持久保存，不能把它们降为缓存，也不要求每个 AGENT 每次载入全项目历史。

## 8. 变更、历史与异常

| 情况 | 模型处理要求 |
| --- | --- |
| 共享设计发生变化 | 新设计版本关联到受影响 wish；保留历史 Candidate 的旧引用，不复制成多个部件 |
| wish 意图或规则改变 | 建立新工程版本，按原生依赖评估相关检查和决定的适用性 |
| 重命名或移动文件 | 核对稳定身份绑定，不能自动生成重复工程元素 |
| 重复身份或引用对象不存在 | 定位冲突与缺失；不按同名、相似文本或目录猜测关联 |
| 实际证据无法读取 | 保留原引用并标明缺口；不能用后来的测试自动替代旧证据 |
| 用户改变关卡结果 | 新 Decision 参与当前开发链，原检查事实和旧发布关联内容保留 |
| 补充已发布产品的工程说明 | 新增补充关联和真实检查时间，旧关联不变，不强制重新发布产品 |

旧模型关系表达当时的工程主张；新判断可以评价或替代其当前适用结论，但不把历史事实改写成从未发生。用户调整的完整语义见 [gate.md](gate.md)。

## 9. 对原 Wish 模型的明确调整

[wish_to_product.sysml](../../wish_to_product.sysml) 已区分 `Wish`、`DeliverableSpec` 和 `ProducedBundle`，这个区分保留。目标设计把实际源文件及版本作为工程内容来源，而不是用 `modelText` 与解析缓存维护多份可独立修改的模型正文。

`TraceLink` 的 source/target 字符串可以成为导出信息，但不是原生链的权威表达。目标链采用原生元素、关系和确定记录引用。`syntaxPassed`、`semanticsPassed` 等汇总需要由真实 CheckResult 和 Decision 支持，其中语言类型语义与工程充分性分开。

原示例的温室 wish、角色分配及未赋值的权限不成为新项目的默认内容。建立模型 usage 不等于已经生成文件、执行检查或获得批准。

## 10. 验收示例

用“断网后保存用户修改，恢复网络后同步”作为一条示例 wish。ProjectModel 中已有客户端、本地存储和同步部件；WishModel 引用这些实际部件，连接离线保存需求、相关设计、确定代码范围、断网验证计划、实际执行及判断。第二条 wish 也涉及本地存储时，应引用同一部件，不再复制一个可独立编辑的存储部件。

| 验收情况 | 应观察到的结果 |
| --- | --- |
| 新建两条 wish | 两个独立原生入口及各自追溯 view，共享项目部件仍只有一个维护来源 |
| 只有文件列表，没有实际组成关系 | 结构核对指出 ProjectModel 的组成内容缺失 |
| 有原生 verify 关系，没有执行结果 | 展示验证计划及未获得的证据，不展示已验证成功 |
| 工程文件编译成功，但少 view | 明确诊断该工程文件的 view 缺口；图片不能代替原生声明 |
| 需求、设计和代码都存在但含义不一致 | 结构事实与 AGENT 的充分性判断分开保存 |
| 共享部件重命名后重新解析 | 两条 wish 仍定位同一部件身份，或报告需要处理的绑定冲突 |
| 旧发布之后修改模型、规则和决定 | 当前链更新；旧关联仍能按原版本读取模型、view、事实和决定 |

本次只定义目标模型契约，没有提交新的可编译 SysML 示例，也没有执行这些验收工作流。
