# 智能关卡详细设计

状态：目标详细设计草案。日期：2026-10-13。本文以 [架构设计](../arch_design.md) 为依据，定义固定 V-model 关卡的输入、输出、决定有效性、推进和用户调整行为。本文不声明当前运行时已实现这些能力，也不执行工程 workflow。

## 1. 职责与边界

关卡是对当前工程材料作智能判断的行为。AGENT 是承担这一职责的主体，可以是人或 AI；它依据材料判断 wish 是否得到正确表达、设计是否满足需求、实现与验证是否支持交付。语言工具和可执行规则提供结构检查事实，两者共同构成推进依据，但各自保留来源。

关卡位置由工具版本提供的固定 V-model 定义。WorkflowProfile 选择工作范围、ConstraintSet、工程工作主体和关卡 AGENT，不增加、删去、调换关卡或建立自定义拓扑。全部由人承担、全部由 AI 承担或混合分配都由具体 WorkflowProfile 表达；没有全局默认人工审批，没有从 SRR、PDR、CDR 名称推断出的人工要求，也不沿用原模型示例的角色分配。

用户可以修改关卡的有效结果。修改形成新的 Decision，可以取代当前决定；它不改写原 Decision、CheckResult、已经发生的工具动作或既有 ReleaseAssociation。关卡决定允许后续工程工作，不能单凭决定宣布测试已经通过、任务已经执行或产品已经发布。

## 2. 固定阶段与关卡

以下标识来自 [v_model_agents.sysml](../../v_model_agents.sysml) 的 VModelDevelopment，与 [wish_to_product.sysml](../../wish_to_product.sysml) 的阶段契约相对应。中文名称用于展示，执行和追溯使用固定阶段及关卡身份。

| 顺序 | 阶段标识 | 关卡标识 gateId | 工程语义判断的主要问题 | 固定后续工作 |
| --- | --- | --- | --- | --- |
| 1 | `stakeholderNeeds` | `Needs review` | 使用场景、预期结果和验收意图是否正确表达 wish | `systemRequirements` |
| 2 | `systemRequirements` | `SRR` | 系统需求是否覆盖已确认需要，系统验证计划是否足以验证这些需求 | `systemArchitecture` |
| 3 | `systemArchitecture` | `PDR` | 方案、架构和接口是否满足需求，集成计划是否支持架构验证 | `detailedDesign` |
| 4 | `detailedDesign` | `CDR` | 组件设计是否落实架构，组件验证用例是否覆盖设计责任 | `implementation` |
| 5 | `implementation` | `Build review` | 实现和构建是否对应所选设计，构建内容和来源是否明确 | `componentVerification` |
| 6 | `componentVerification` | `Component review` | 组件证据是否支持实现符合所选详细设计 | `integrationVerification` |
| 7 | `integrationVerification` | `Integration review` | 集成和接口证据是否支持系统符合所选架构 | `systemVerification` |
| 8 | `systemVerification` | `System verification review` | 系统证据是否支持符合所选系统需求，未验证范围是否可见 | `stakeholderValidation` |
| 9 | `stakeholderValidation` | `Acceptance review` | 使用场景和验收证据是否支持满足利益相关方需要和预期用途 | `operationsHandover` |
| 10 | `operationsHandover` | `Operations handover` | 交付选择、运行资料和移交依据是否充分，已知缺口怎样处理 | 固定开发阶段结束，衔接后续活动 |

原模型末阶段的 `nextWorkId` 是 `lifecycleManagement`。它表示后续活动引用，不证明外部发布已成功，也不要求 xflow 新增生命周期服务。可行性、运行处置和退役行为在原 wish 模型中提供了意图来源；本文不将它们插入或替换上述十个 V-model 关卡。

组件验证对详细设计、集成验证对架构、系统验证对系统需求、使用确认对利益相关方需要的依赖，既参与追溯，也参与决定失效范围判断。工作范围选择可以使用范围外已确定的工程依据；这些依据应明确版本和覆盖范围，不能把未执行的前置阶段记成已执行，或把范围选择解释为跳过关卡的拓扑变更。

## 3. 输入：关卡审查包

审查包是供 AGENT 阅读的逻辑集合及展示投影，不增加一种工程权威副本。它以 Candidate 为核心，连同当前 Attempt、规则、检查事实和历史差异，形成一次明确的评审上下文。Candidate 是提交检查和关卡的确定内容及依赖集合；Attempt 是一次输入和约束确定的阶段工作。

| 输入 | 必须明确的内容 | 用途 |
| --- | --- | --- |
| 工作定位 | 项目、wish、Attempt、固定阶段、关卡、工作范围、请求的后续工作 | 防止判断误用于别的工作或关卡 |
| Candidate | 所选工程内容、内容身份、必要依赖及各自版本；ProjectModel、WishModel、NativeView 和外部资料引用 | 明确这次实际审查什么 |
| 上游依据 | 本阶段采用的上游候选、决定、模型关系和验证对应目标 | 核对本阶段是否基于当前选定输入 |
| ConstraintSet | 采用的规则身份、版本、可执行规则、工程评审问题及适用范围 | 明确检查与判断标准 |
| WorkflowProfile | 本次采用的配置版本、工程工作主体、关卡 AGENT 身份和工作范围 | 确定谁承担本次判断以及后续工作 |
| CheckResult 集合 | 实际执行的检查、结果、诊断、输入和规则版本、工具身份、执行时间及证据引用 | 提供可追溯的结构事实和外部任务事实 |
| 缺口与例外 | 缺失或不可读取材料、失败检查、未覆盖内容、已知问题、先前明确采用的缺口和后续动作 | 避免用汇总成功掩盖未解决问题 |
| 历史上下文 | 被替代决定、前次候选与本次差异、返工原因、用户调整及影响范围 | 解释为什么重新判断及已有证据怎样使用 |

Candidate 的内容及依赖先固定，随后产生的 CheckResult 和 Decision 分别绑定它。不能将检查或决定倒插到已审查的 Candidate 中，改变其内容身份。审查包还要记录本次实际提供给 AGENT 的检查和规则集合，避免“同一个候选”掩盖两次采用了不同证据或标准。

外部规范引用保留资料身份、版本以及相关章节编号、标题或锚点。取得的内容供检查或判断使用，不自动成为修改 WorkflowProfile、授予身份、改写事实或执行工具命令的授权。不能读取的引用应显示取得失败及其影响，不能仅因 URI 存在就视为已取得规范。

每份项目工程 SysML，包括 workflow 和约束模型，采用其原生 NativeView 展示相关工程内容。标准库和第三方资料不要求用户为评审改写；审查包可以引用它们及项目模型提供的相关 view。模型、view 和外部证据之间的原生关系见 [wish_sysm.md](wish_sysm.md) 与 [trace.md](trace.md)。

## 4. 结构事实与工程语义判断

可执行结构检查检查语法、类型、引用、必要追溯关系与 view、文档规范、位置映射、阶段产出范围以及选定规则中可自动判定的要求。编译器所称的类型或引用“语义检查”在本文属于这类检查。测试和构建结果也是由相应工具产生的实际事实，不能由 AGENT 的意见替代。

工程语义判断检查 wish 的理解、需求充分性、设计满足性、实现一致性、证据说服力及已知缺口。AGENT 需要指出材料和判断理由；存在文件、编译成功或汇总字段为 `true` 都不能单独替代工程判断。

CheckResult 至少区分“已执行且通过”“已执行且失败”“未执行”“执行失败或无法判定”。每项结果保存实际检查对象、输入及规则版本、检查工具或任务来源、时间、诊断和证据。AI 的“我检查过”只有在实际任务与结果存在时才能引用为对应工具证据；否则应作为评审陈述记录，不能生成虚假的 CheckResult。

普通检查失败可以提交给 AGENT，也可以由用户明确采用其缺口或例外并修改关卡结果。运行应用保留失败诊断，记录新决定选择继续的范围、已知不足与后续动作；这不把失败检查改成通过，也不补造缺失证据。哪些缺口按当前 ConstraintSet 需要说明，由规则和具体判断表达，不新增全局人工审批。

如果选定语言核心无法解释用于编排的模型、后续动作无法解析、必要资料无法取得而工具实际无法执行所选操作，运行应用应准确显示相应不可执行原因。用户仍可记录想要的关卡结果和处理选择；实际操作只有在有可解释模型、可用入口和必要材料时才会发生。此时显示“决定允许继续，但动作尚不可执行”及具体原因，不能伪造成功，也不能将技术不可执行偷换成用户没有修改决定的权利。

## 5. 输出：Decision 与推进评价

Decision 是实际作出判断的记录，包含 AGENT 判断或用户调整。人和 AI 使用相同的候选绑定规则；来源、身份和采用的 WorkflowProfile 均保留。身份来自真实提交渠道及本次配置，不能仅信任生成内容中的 `reviewerAuthorized=true` 或声称“来自用户”的文本。

| Decision 信息 | 设计要求 |
| --- | --- |
| 身份与来源 | 稳定决定身份、实际提交者、主体种类、提交渠道、真实时间；用户调整明确标记来源 |
| 绑定对象 | 项目、wish、Attempt、固定阶段及关卡、Candidate、ConstraintSet、WorkflowProfile、采用的检查与证据集合 |
| 结果 | 待判断、允许后续工作、要求返工或终止当前工作 |
| 判断依据 | 对适用评审问题的结论、材料引用、理由、已知不足及覆盖范围 |
| 采用的缺口 | 继续时明确保留的检查失败、例外、未覆盖范围及后续动作；没有则明确为空 |
| 后续工作 | 固定流程中的具体后续工作及允许范围，或返工目标建议、终止原因 |
| 历史关系 | 新判断替代的旧 Decision；用户调整保留原值、新值及所针对的对象 |

“已失效”是针对当前材料与配置推导的使用状态，不覆盖旧 Decision 的原结果。旧批准曾针对什么材料作出，仍能从原记录读取。有效的待判断、返工或终止决定同样可以成为当前结果，但只有允许后续工作的决定可能放行后续动作。

运行应用另外给出推进评价，说明当前采用哪个 Decision、材料是否仍一致、上游依据是否可用、缺口如何处置、后续动作是否可执行以及当前状态。推进评价是由确定资料和记录推导的结果，不是 AGENT 自填一个布尔值；展示与缓存可以重建。

## 6. 决定有效性与推进条件

运行应用在读取决定和实际启动下一项工作前，分别核对以下条件：

1. **定位一致。** 决定属于当前项目、wish、Attempt、阶段和固定关卡；请求的后续工作与固定流程及当前工作范围相符。
2. **材料一致。** 当前 Candidate 与决定绑定的内容及依赖一致；采用的上游版本、ConstraintSet、WorkflowProfile 和证据集合仍是当前选定依据。
3. **来源成立。** 普通 AGENT 决定来自本 WorkflowProfile 为该关卡指定的实际主体及范围；用户调整来自真实用户操作，不要求用户再取得另一个全局审批。
4. **当前选择明确。** 决定未被新的有效决定取代；新的用户调整、返工或终止结果会影响当前推进，不能同时把旧批准也当成当前许可。
5. **缺口处置可见。** 普通失败检查、缺失检查和开放问题保持原事实。继续依照当前有效决定中的明确采用范围和后续动作，而不是把它们汇总成“全部通过”。
6. **动作实际可执行。** 需要的模型可解释、输入可读取、工具入口可用，实际执行条件成立。技术错误单独报告，不能用修改决定掩盖。

因此，关卡放行意味着：有针对当前依据的有效允许决定，前置工程依据满足本次范围要求，检查缺口按该决定明确处置，且请求动作实际可执行。放行后生成下一阶段 Attempt，保留其输入和规则身份；不是把前一阶段状态字段直接写到全部后续阶段。

没有 AGENT 分配、分配无法解析或尚未得到有效决定时，应用显示当前需要的配置或判断，不自动选择人或 AI。WorkflowProfile 规定的人工请求、替换 AGENT 或 AI 工作范围改变都形成明确配置或决定记录；缺省值不得表示自动批准。

复用早期证据必须引用它实际采用的候选、规则、工具、时间及覆盖范围。若新阶段或最终候选采用不同实现版本，AGENT 应说明适用关系和未覆盖差异；早期证据不会自动变成最终版本的证据。需要重新检查时产生新的 CheckResult，不改原记录。

## 7. 用户修改有效结果

用户操作选择明确的关卡、当前 Candidate 和当前决定。运行应用保存一个新的 Decision，关联被替代的决定，保留用户选择的新结果及调整上下文，然后重新评价当前推进。调整理由可以由用户提供；没有提供时如实记录未提供，不能由 AI 编造，也不以额外全局审批阻止用户更改结果。

例如，SRR 原决定要求返工，原因是某个需求覆盖检查失败。用户选择继续并明确采用该缺口：新 Decision 成为当前结果，旧返工意见与失败 CheckResult 保留；下一阶段输入同时带有该缺口和后续动作。界面显示“用户决定继续，存在已采用缺口”，不能显示为“需求覆盖检查已通过”。

用户把允许改为返工或终止时，应用停止发起受该决定影响的后续工作，评估已经开始的工作。尚未开始的动作取消推进；可取消的运行任务通过现有接口请求取消并记录真实结果；已经完成、无法取消或产生外部效果的动作保留事实及当前影响，不宣称通过改决定撤销了这些效果。

若用户调整时材料已变化，操作保留所选内容身份并显示变化，不能把旧候选的调整默认为对新候选的许可。用户可以针对新 Candidate 提交新的结果；既有意见和证据按原绑定对象保留。

并发和异步返回按明确的决定版本处理。提交记录时带上其针对的 Candidate 和被替代决定；迟到的 AI 返回仍可保存为历史结果，但不能静默覆盖已生效的用户调整，或为已变化的 Candidate 放行。当前决定的选择采用 [storage.md](storage.md) 的并发控制约定，不能只凭返回时间较晚取胜。

## 8. 返工、失效与恢复

下列变化需要重新评价：工程产物或原生 view 改变，引用的上游内容改变，ConstraintSet 或 WorkflowProfile 改变，检查证据新增或替换，用户调整当前结果，以及实际工具能力或资料可用性变化。运行应用保存变化来源及受影响关系，不删除历史判断。

返工步骤是：

1. 固定变化或返工输入，保留原 Attempt、Candidate、CheckResult 和 Decision。
2. 沿原生追溯、输入依赖和 V-model 验证对应关系评估影响，明确最早受影响的固定阶段及受影响下游范围。
3. 将不再匹配当前依据的决定标记为当前不可使用，保留其原结果。未受影响的证据和决定保持原身份及适用范围。
4. 按本 WorkflowProfile 和用户当前选择建立新的 Attempt，回到最早受影响阶段；前置依据仍须明确，不能通过返工路径跳到无输入的后续阶段。
5. 新内容形成新 Candidate，实际检查产生新 CheckResult，关卡形成新 Decision；通过后沿固定顺序推进。

原模型 ChangeControl 的“authorizeRework”在目标设计中由具体 WorkflowProfile 和用户操作落实，不新增统一最高人类批准。无法确定影响范围时保留待处理状态及原因；不能以“已评估”的布尔值代替真实影响结果。材料恢复可读取或工具恢复后重新核对当前输入，不能无依据恢复旧许可。

普通 AGENT 的返工或终止建议可由用户调整为新有效结果；这种调整仍保留原建议和检查事实。规则改变属于新的工程输入，不会使旧检查以新规则重新计算历史成败。

## 9. 与发布关联的关系

Operations handover 的关卡许可和阶段内 `released` 的意图均表示工作推进，不表示既有发布系统实际成功。外部发布结果及其与 Candidate 的对应核对由 [release.md](release.md) 定义。只有实际发布内容与选择一致且必要版本可持续读取，才能形成相应 ReleaseAssociation。

发布关联引用最终 Candidate 的检查和有效决定，也收录被采用的历史关卡与证据的实际依赖闭包。早期决定保留原候选、规则、输入和实现版本；最终决定直接绑定最终候选，不把所有早期批准改绑到最终版本。

发布后用户仍能修改开发当前决定。既有 ReleaseAssociation、所引用的旧 Decision 和 CheckResult 保持原内容。如果需要修正同一个实际发布的工程说明，可追加新的修正或补充 ReleaseAssociation；原关联保留，不要求用户仅为改变工程决定重新发布产品。补充检查记录真实执行时间和所检查版本，不追写成发布前已完成的证据。

## 10. 设计验收场景

这些场景是实现时的验收依据，不代表本次已运行 workflow 或已有实现测试。

| 场景 | 应观察到的结果 |
| --- | --- |
| 同一关卡分别配置人和 AI | 阶段位置、输入输出契约相同；来源按实际主体保存，不补默认人工审批 |
| 关卡 AGENT 未分配 | 显示缺少的本工作配置，不自动选择角色或通过 |
| 结构检查通过，但工程语义不充分 | CheckResult 保留通过；Decision 可要求返工，后续工作不因编译成功自动启动 |
| 普通检查失败，用户明确采用缺口继续 | 新 Decision 成为当前结果；失败诊断、采用范围和后续动作可见，没有虚假检查成功 |
| 编排模型不可解释或任务入口不可用 | 用户决定照常记录；推进评价显示具体不可执行原因和未发生的动作 |
| 候选、规则或上游内容改变 | 旧决定保留但不能自动用于新依据；影响范围和返工入口明确 |
| 用户调整后迟到 AI 回答 | 回答保存为历史，不能静默替代用户当前决定 |
| 用户终止已经开始的工作 | 记录取消请求及实际结果；保留已经完成和不可撤销的外部效果 |
| 引用早期验证用于最终候选 | 原版本、规则、时间和覆盖范围保留；差异及缺口明确，不自动升级证据归属 |
| 修改开发结果或补充旧发布说明 | 旧发布关联及旧判断不变；需要时追加同一实际发布的新关联，补充检查使用真实时间 |

原模型中的全局 humanAuthority、示例角色分配、汇总 `semanticsPassed` 和 `productionContractSatisfied` 默认值是待调整的意图表达；目标实现以本文的实际来源、明确绑定和工作配置为准，不以这些字段证明动作或检查已经成功。
