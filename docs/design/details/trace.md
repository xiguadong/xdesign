# 原生追溯与工程记录详细设计

状态：设计草案。日期：2026-10-13。依据：[架构设计](../arch_design.md)。本文定义追溯内容、版本与事实怎样连接；流程推进由 [V-model 设计](v_model_sysml.md) 负责，资料读写由 [存储设计](storage.md) 负责，实际发布关联由 [发布设计](release.md) 负责。

## 1. 职责与共同术语

追溯要解释一项工程主张的来源、对象和支持程度。例如，某个缓存部件为何满足离线保存需求，实际验证使用了哪个实现，以及谁依据什么决定继续工作。图上连通不是主张已经成立的证明。

| 术语 | 本文中的含义 |
| --- | --- |
| Candidate | 选定工程内容及其必要依赖的确定集合；包含本次采用的版本，不跟随工作区后续编辑 |
| Attempt | 一次输入和规则确定的阶段工作尝试；其内可以包含多个实际执行或检查，产生的 Candidate 与结果分别保留 |
| CheckResult | 可执行检查产生的事实，包括方法、实际输入、观察与覆盖；不是关卡决定 |
| Decision | 人或 AI 对确定 Candidate 作出的判断，包含理由、依据及允许的后续工作 |
| ReleaseAssociation | 项目既有实际发布与确定 MBSE 依据的不可变关联；不是另一套产品发布 |
| NativeView | 原生 SysML view usage，选择要展示的模型元素和关系；图片及卡片是其派生展示 |

公共追溯类型和关系解释属于工具的固定机制。项目组成、每条 wish 的链、NativeView 和确定版本引用属于持久工程资料，会在开发中生成和更新。工程语义不能仅保存在一个外部数据库的 ID 列表里，再由界面猜出连接。

## 2. 原生语义链的内容契约

### 2.1 节点是有类型的模型元素

| 链中对象 | 原生表达与职责 |
| --- | --- |
| wish 意图 | 领域定义的 Wish usage，连接原始提交来源；建模意图可以修订，原提交保持原内容 |
| 需求 | 原生 requirement usage，具有明确语句、主体和适用范围 |
| 项目设计 | 项目模型中的 part、port、interface、action 等原生元素；wish 引用实际共享元素 |
| 实现材料 | 有类型的实现引用节点，选择代码、构建或其他实现材料的实际版本 |
| 验证计划 | 原生 verification definition/usage 及其 objective；计划与执行是两个对象 |
| 使用确认计划 | 有类型的计划与目标，选择 wish 意图、使用情境和判断标准 |
| Candidate 与实际记录引用 | 公共追溯类型的原生 usage，选择工程对象并连接 Attempt、CheckResult、Decision 或 ReleaseAssociation 的原记录 |
| 外部材料 | 有类型的材料及版本引用；可附加文档局部定位，不把文件内容冒充 SysML namespace import |

节点的外部记录标识、URI 或内容摘要只负责定位和核对。原生节点之间仍使用可解析的引用及关系。不能用 `requirements = [外部ID...]`、`evidence = [外部ID...]` 这类字符串列表替代需求、验证目标、证据引用节点和它们的语义关系。

稳定身份独立于显示名称和解析器临时编号。工具从工程资料中读取明确身份，并保留名称、源位置和类型。重命名不能自动生成一个新工程对象；无法确定是否为原对象时，必须形成明确的身份调整，不能按相同标题合并。

### 2.2 关系保留原生种类和工程含义

| 工程含义 | 表达约定 | 不能推导出的结论 |
| --- | --- | --- |
| 系统组成、类型与职责 | 原生组成、typing、action usage 与 `perform` 等关系 | 导入一个包不表示拥有或实例化包内全部部件 |
| 需求分解或 wish 细化 | 适用的原生需求结构；跨对象细化采用命名 dependency 和固定领域角色 | 图上的父子显示不能代替实际分解或细化关系 |
| 设计满足需求 | 原生 `satisfy`，保留满足主体和目标需求 | 声明满足不等于已经执行验证 |
| 验证计划针对需求 | verification objective 中的原生 `verify` | 定义目标不等于该 case 已执行或通过 |
| 工作顺序与返工 | 流程中的原生 succession、transition 及条件 | 追溯依赖不是执行顺序；合法返工回路不能被删除 |
| 实现某项设计 | 实现材料节点与设计之间的命名 dependency，采用明确的 `implements` 领域角色 | 文件名或目录相近不能建立实现主张 |
| 实际尝试执行计划 | Attempt 引用节点与选定计划、Candidate 之间的明确关系 | 一个日志附件不能自行覆盖所有验证 case |
| 检查、评估与证据支持 | CheckResult、Decision、材料节点与被检查 Candidate、规则和目标之间的领域关系 | 工具成功退出不能自行产生语义判断或放行决定 |
| 用户调整已有决定 | 新 Decision 明确引用被替代 Decision、Candidate 和调整范围 | 修改当前有效结果不能删除旧决定或改写检查事实 |
| 发布的工程依据 | ReleaseAssociation 引用节点连接实际发布引用和选定工程依据 | 完成 AGENT 判断不能证明外部发布系统已经成功发布 |

应用角色是命名原生 dependency 的领域解释，不把它重新标成另一种标准关系。解析结果和详情展示要同时保留原生关系种类、关系自身身份、源与目标、领域角色、理由及源位置。多目标关系仍是同一个原生关系；分拆显示不得制造多条独立工程主张。

## 3. 独立 wish 链与共享项目元素

每条 wish 拥有独立命名空间、原生追溯模型及 NativeView。wish 文件维护其意图、独有需求及追溯关系；共享部件、行为、需求或验证计划留在原来的维护来源，通过原生引用参与其他 wish。独立链不要求复制一套完整系统模型。

例如，离线保存 wish 与同步冲突 wish 可以同时引用项目模型的同一个缓存部件。两个 wish 各自声明该部件与其需求的关系，各自选择验证和决定；一个 wish 完成不会自动完成另一个。

每个关系有一个维护来源。跨文件关系在声明方文件维护；共享元素的定义由其所属模型维护。另一条 wish 只能引用该元素，不能把借用的定义当作本 wish 可独立编辑的副本。

导入仅使已有模型成员可引用，不建立额外实例。NativeView 显式选择 wish 的本地元素、跨文件关系及所需共享元素；范围外的成员可以继续展开。渲染器不得把导入全部库当作该 wish 的工程范围，也不得用省略后的显示判断关系不存在。

共享内容不可用、被撤去或身份无法解析时，受影响 wish 保留原引用和缺口。系统不通过复制旧显示结果、按名称寻找替代部件或默默删边来恢复连通。

## 4. 确定版本与 Candidate

一次 Candidate 的选择来源于原生工程资料，包含本次目标、工程元素、关系、规则及必要材料依赖。应用解析和核对这些选择，保存当时实际读到的来源与版本。记录中的历史选择是当次观察，不成为另一份可独立编辑的模型权威。

确定版本至少能回答：

- 选中了哪个原生对象、哪项关系，以及它们来自哪个源文件版本。
- 哪些共享定义、工具语言依赖和用户规则参与了此次解释。
- 哪个文档、实现或证据版本被选择，能否恢复对应内容。
- 哪个原生 NativeView 表达本次范围，哪些内容被明确省略。

原生工程身份负责识别对象；版本和内容摘要负责识别当次内容。当前工作路径、可移动的 Git tag 或显示名称不能单独选定历史内容。一个同名需求的新语句也不能沿用旧检查的适用性。

Candidate 在开始检查和判断前确定。检查和 Decision 必须引用同一候选；若判断者另读了补充材料，该材料必须成为明确的补充选择，随后重新确定候选及需要补做的检查，不能事后声称原候选已经包含它。

Candidate 摘要不包含自己的摘要，也不包含随后产生的 CheckResult、Decision 或 ReleaseAssociation。后来加入的原生记录引用指向实际发生时的工程版本；它不会反向改变过去检查了什么。验证新引用的结构可以产生单独的 CheckResult，不能让一条记录成为证明自身正确的循环依据。

接入记录引用所产生的结构 CheckResult，可以由后续 Candidate 或 ReleaseAssociation 明确选择，不要求在同一个已检查模型版本中再追加它自己的检查引用。新增结构事实通过确定记录参与依据，无需反复修改同一文件来容纳证明自身的记录。

## 5. 实际记录怎样进入原生链

### 5.1 事实与模型引用分工

Attempt、CheckResult、Decision 和 ReleaseAssociation 的实际事实追加保存于记录存储。原生链中持久保存对应的类型化引用节点及关系，连接被执行计划、被检查 Candidate、判断主体、依据材料和工程目标。引用节点可带来源定位和必要摘要，但不能作为第二份可编辑事实账本。

先保存事实并取得可核对的确定引用，再以受控模型修改接入链。保存事实成功而原生模型更新失败时，事实继续保留，接入工作可以恢复；此时视图要显示“已有记录尚未建立原生关联”。模型引用存在但原记录无法读取时，显示缺失或不完整，不能从节点名称补造执行结果。

### 5.2 检查和决定的内容契约

| 记录 | 必须保留的内容 |
| --- | --- |
| Attempt | 固定阶段、工作范围、执行主体、实际输入与规则、开始与观察时间；其内实际执行和检查、产出的 Candidate 及已知效果分别保留，未确认结果明确保留不确定性 |
| CheckResult | 实际执行的检查与方法版本、Candidate、执行观察、结果、覆盖范围、诊断及证据位置；未执行不能记录为通过 |
| Decision | 判断者及人/AI 种类、Candidate、适用语义标准、所读检查与证据、判断结果、理由、限制和允许的下一项工作；用户调整未提供理由时如实标记 |
| 用户新的 Decision | 被替代的 Decision、用户身份、确定 Candidate、修改理由、范围与后续工作；未提供理由时如实标记，原判断继续保留 |
| ReleaseAssociation | 实际发布身份、实际发布内容选择、确定 MBSE 依据及核对结果；具体确认流程见发布设计 |

检查只说明它执行的事实，语义充分性由分配的人或 AI 判断。AI 使用的任务、上下文及模型/方法身份随实际记录保留；重新调用可能形成不同判断，不能把新输出覆盖到旧记录上。

用户可以改变当前有效决定，包括接受已知不足或要求重新工作。新的 Decision 引用原检查和原判断，保留真实诊断及未执行项目；“用户允许继续”与“工具检查通过”分别可见。决定是否有可执行的下一步由流程核对材料与执行前提，不能通过调整决定生成不存在的文件或执行证据。

用户未提供调整理由时记录未提供，不由 AI 编造，也不设置必须补充理由或再次审批的全局门槛。

同一个实际发布可以追加修正或补充 ReleaseAssociation，旧关联保持原内容。补充检查和判断保留真实发生时间，不能被展示为发布当时已经完成的工作；调整 MBSE 依据不强制项目重新发布产品。

实际 ReleaseAssociation 确认后，wish 链可以在新的模型版本接入真实发布引用，成为可定位的完成端点。原 Candidate 和发布关联不回写，旧快照不被宣称已经包含后来事实；接入这一端点也不要求再次封存一个包含自身关联的新发布依据。

## 6. 文档局部定位是材料引用的子需求

文档是工程材料，相关章节是选择该材料的具体范围。一个版本的文档只维护一份内容，两条 wish 可以分别选择不同章节。

| 局部引用内容 | 约定 |
| --- | --- |
| 文档身份与版本 | 指向可恢复的确定文档内容；固定完整文档版本，不仅保存会更新的地址 |
| 选择位置 | 明确选择器种类和位置；有稳定章节标识时使用标识，否则使用该版本中的章节号、页/段落或明确范围 |
| 关系上下文 | 关联具体原生元素或命名关系，说明该章节支持什么工程主张 |
| 相关理由 | 保存为什么采用此处，而非只挂一个整篇文档链接 |
| 定位观察 | 保留定位成功、缺失或无法自动解释的结果，不把打不开的章节当作已阅读依据 |

当一个共享设计支持多个 wish 时，需求与设计之间的关系可以各自附带不同章节引用和理由。设计节点的通用说明不替代这种关系上的具体相关性。

外部 URI 是资源定位，不是原生包导入。解析器负责提取类型和原生选择；资料适配负责读取选定版本及定位章节。不能用正则查找一串 URL 后自行生成原生关系，也不因文档出现相似关键词就推断设计满足需求。

章节发生移动时，旧版本中的定位保持原义；采用新版本需要新选择。新版本无法找到原章节时，记录缺口并交给相应工作处理，不自动退回整篇文档作为同一个已满足引用。片段预览是派生内容，不能替代确定的源文档。

## 7. 变更影响与历史适用性

影响从实际选定依赖传播，而不是从文件修改时间或界面位置传播。当前有效性的计算读取原生对象与关系、Candidate 选择和实际记录；它不重写旧记录的结果。

1. 标明发生变化的内容及其旧选择和新选择，包括工程元素、关系、文档、规则或共享定义。
2. 找到实际选择了这些内容的 Candidate、CheckResult 和 Decision。
3. 沿原生依赖与依据关系找出受影响的 wish 和阶段，区分确定依赖与需要 AGENT 判断的影响。
4. 为当前开发工作显示不再适用的决定、所缺检查及需判断的问题；由流程选择返工或重新判断。
5. 新尝试、新检查及新 Decision 继续追加，历史视图仍按原选择解释旧结果。

修改被选需求语句、满足关系或相关证据，可能影响当前放行；只改变另一条 wish 的独立内容不自动撤销本范围。发布新规则版本本身也不改变仍选用旧规则的记录；显式采用新规则或发现旧规则存在相关缺陷时，才为当前范围重新评估。

已经确认的 ReleaseAssociation 保持不变。后来发现问题时，新增影响或修正记录，并向读者说明；不能把原关联内部的旧 Decision 改成一个新结论。

## 8. 读写行为与失败处理

| 操作 | 读写行为 | 失败时保留什么 |
| --- | --- | --- |
| 建立 wish 链 | 读取来源及共享项目元素，生成独立原生模型和 view，经语言检查后受控保存 | 原提交、候选材料、诊断；不能留下一个伪称验证成功的链 |
| 增改关系 | 选择原生端点及关系种类，保存关系自身身份、理由、版本与对应 view | 原源文件；无效端点、类型或并发修改不能静默修复或覆盖 |
| 接入观察与决定 | 先保存事实，再生成类型化引用节点及关系，记录接入结果 | 原事实及可恢复的接入尝试；不重复执行已经发生的工作来补一条边 |
| 读取 wish | 解析选定原生链与 view，核对记录及材料版本，标明范围、缺口和历史适用性 | 来源文本和诊断；不能把旧图当作当前成功结果 |
| 调整当前决定 | 追加用户 Decision，明确被替代决定及范围，重新计算当前影响 | 原决定、检查、已发生效果和已确认发布关联 |

记录读取缺失、原生解析失败、实际执行结果不确定是不同问题。前者保留未解析的引用，第二种保留源及诊断，第三种等待核对已有执行效果；不得统一成“失败所以安全重试”。

读取范围可以限定为一条 wish 的选择及依赖。省略的节点、范围外端点和真正无法解析的引用必须区分；分页或展示预算不能被解释为追溯链缺失。详见存储设计的索引与读取约定。

## 9. 验收例

| 场景 | 应观察到的结果 |
| --- | --- |
| 离线保存与同步冲突引用同一缓存部件 | 两条 wish 各有独立 native 链及 view，部件只有一个原生身份，关系和完成范围分别可查 |
| 只声明 `satisfy` 和 `verify`，没有运行 | 能定位设计主张和计划目标，实际观察缺口明确；没有通过或完成结论 |
| 为旧实现产生测试结果，随后修改代码 | 原 CheckResult 仍指向旧实现版本；当前 wish 不把它显示为检查了新代码 |
| 增加一次检查的原生引用节点 | 检查目标仍是原 Candidate；新增节点有独立结构来源，不产生自引用摘要或无穷失效 |
| 结构检查通过，AI 判断需求不充分 | CheckResult 和返工 Decision 分别保留，无法用“编译通过”覆盖判断 |
| 用户改变关卡结论 | 新 Decision 成为当前选择，原检查失败和原判断保持可查，旧发布关联不被修改 |
| 两条关系引用同一文档不同章节 | 共享一份文档版本，分别定位章节并展示关系理由；章节丢失时出现明确缺口 |
| 修改与某 Candidate 无关的 wish | 相关独立判断继续适用，影响范围不因整仓库编辑自动扩大 |
| 事实已保存但写原生引用时冲突 | 事实不丢失、不重复运行；接入可恢复，视图不伪造完整链 |
| 为同一实际发布补做评审 | 追加新的关联及真实评审时间，原关联和产品发布不被覆盖或重发 |
