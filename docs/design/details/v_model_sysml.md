# V-model SysML 详细设计

状态：目标详细设计草案。日期：2026-10-13。依据：[架构设计](../arch_design.md)。本文定义固定流程怎样成为可执行的工程过程，不声明当前运行时已经实现这些行为。

## 1. 职责和模型来源

工具版本提供固定的 V-model 阶段、关卡位置、验证对应关系和返工路径。用户项目提供本次工作的范围、阶段输入、用户约束以及执行主体和关卡 AGENT 的分配。运行应用读取两者，组织实际工作并记录发生的结果。

本文负责流程表达、阶段契约和执行顺序；关卡输入、决定有效性及用户调整由 [gate.md](gate.md) 定义。模型与 view 契约见 [wish_sysm.md](wish_sysm.md)，追溯和历史见 [trace.md](trace.md)。共同对象术语见 [overview.md](overview.md)。

两份原模型提供意图来源，保持原文件不变：

| 来源 | 保留的意图 | 目标设计中的落实 |
| --- | --- | --- |
| [v_model_agents.sysml](../../v_model_agents.sysml) 的 `VModelDevelopment` | 十阶段顺序、阶段关卡和 V 形验证对应关系 | 工具版本中的唯一流程定义 |
| `AgentStage`、`ReviewAgent` | 工作后审查、决定绑定材料、满足条件才放行 | 阶段尝试提交 Candidate，应用核对实际 CheckResult 和有效 Decision |
| `DecisionAgent`、`ChangeControl` | 人或 AI 判断、变更评估与返工 | WorkflowProfile 分配主体，原生依赖支持影响评估 |
| [wish_to_product.sysml](../../wish_to_product.sysml) 的 `DeliverableSpec`、`ProduceDeliverable`、`ContractedVModelDevelopment` | 预期产物与实际产物分开、阶段生产读取上游材料和规范 | ConstraintSet 给出阶段契约，实际文件及关系形成 Candidate |

原模型中的说明性 action、未赋值的权限、检查布尔字段和示例角色分配不是已执行事实。目标实现不得把它们自动解释为成功、授权或默认策略。

## 2. 固定流程与 WorkflowProfile

### 2.1 工具定义

工具中的 `VModelDevelopment` 是可复用行为定义；项目的 workflow 使用该定义，并绑定自己的参与者、范围和规则。工具发布应只有一个维护来源，不能同时加载原两份文件中重复的 `VModelAgents` 定义作为两套可独立改变的流程。

固定内容包括：阶段身份和顺序、阶段的关卡身份、验证对应关系、允许的返工目标，以及运行应用支持的流程解释方式。项目接入后使用选定工具版本；本机工具安装更新不自动改变已有项目。

项目约束可以要求更多材料或改变评审标准，但不重新定义 V-model 的阶段顺序、增删关卡或改变 `succession` 的含义。工具开发项目可以生产新的候选流程；该候选在完成工具发布前不替换当前项目使用的执行机制。

### 2.2 项目配置

WorkflowProfile 是使用固定流程的逻辑配置，不要求单独的新文件或目录。若以工程 SysML 保存，也必须具有自己的 NativeView。

| 配置项 | 必须能确定的内容 |
| --- | --- |
| 流程引用 | 项目绑定的工具和固定 V-model 定义 |
| 工作范围 | 参与的 wish、项目部件及本次增量范围 |
| 阶段工作主体 | 每个待执行阶段由哪个人、AI 或既有工具执行工作 |
| 关卡 AGENT | 每个待判断关卡的人或 AI 身份，以及本 workflow 的授权范围 |
| 参与安排 | 人工参与、接管和决定调整的安排；不设全局人工或 AI 默认 |
| 阶段规则选择 | 本次阶段使用的 ConstraintSet 和外部规范版本 |
| 工程位置与任务绑定 | 项目既有模型、文档和代码位置，以及需要调用的已有任务入口 |

工作主体和关卡 AGENT 可以相同，也可以不同。AGENT 的职责是智能判断，不能用主体名称或 `kind = ai` 推断它拥有决定权。缺少待执行阶段所需的主体、规则或材料映射时，给出配置诊断并等待补齐，不自动分配人、AI 或批准结果。

应用只接受配置已知阶段、关卡和绑定位置的 profile。用户配置试图重定义固定拓扑时，应报告不兼容的定义位置，而不是悄悄运行另一条流程。

## 3. 固定阶段及工程职责

下表保持源模型的阶段和 `gateId`。产物列说明该阶段的工程职责，具体材料形式、数量、命名和位置由选定 ConstraintSet 规定，不要求每个阶段都新建一整套独立文件。

| 阶段身份 | 主要工作与审查材料 | 关卡身份 | 正常后续阶段 |
| --- | --- | --- | --- |
| `stakeholderNeeds` | wish 理解、利益相关方、使用场景、预期用途、验收意图与未决问题 | `Needs review` | `systemRequirements` |
| `systemRequirements` | 系统需求、可判断的要求、需求关系、系统验证计划 | `SRR` | `systemArchitecture` |
| `systemArchitecture` | 部件、接口、分配、方案理由及集成计划 | `PDR` | `detailedDesign` |
| `detailedDesign` | 组件结构与行为、设计约束及组件验证计划 | `CDR` | `implementation` |
| `implementation` | 实现、配置、构建材料及设计到实现的引用 | `Build review` | `componentVerification` |
| `componentVerification` | 对实际组件的检查，关联详细设计和组件验证计划 | `Component review` | `integrationVerification` |
| `integrationVerification` | 集成配置、接口检查和异常处理，关联架构及集成计划 | `Integration review` | `systemVerification` |
| `systemVerification` | 系统需求覆盖、实际执行证据及问题处置 | `System verification review` | `stakeholderValidation` |
| `stakeholderValidation` | 对预期用途、场景和验收意图的使用确认及剩余问题判断 | `Acceptance review` | `operationsHandover` |
| `operationsHandover` | 交付配置、使用维护材料、移交范围及既有发布关联所需依据 | `Operations handover` | 本次开发过程完成，交由项目后续生命周期工作 |

最后一个阶段在源模型中指向 `lifecycleManagement`。它是后续生命周期工作的标识，不是 xflow 创建产品发布的命令。阶段放行不证明 CI 已执行、产品已发布或 wish 已完成。

固定的 V 形对应关系是：

- 组件验证对应详细设计。
- 集成验证对应架构和接口。
- 系统验证对应系统需求。
- 使用确认对应利益相关方需求和预期用途。

这些是工程追溯关系，不是跳过中间阶段的执行边。验证阶段的 Candidate 应同时包含被验证的实际实现版本和所依据的设计、需求或验收材料，不能只记住上一阶段的单个字符串基线。

## 4. 原生模型的执行契约

### 4.1 读取与解释

SysML 工具进程先加载项目固定的工具和语言依赖，返回原生元素、关系、view 和诊断。运行应用从选定 V-model 定义读取阶段与流程关系，绑定 WorkflowProfile；解析表示属于可重建缓存，不成为第二份可以编辑的流程定义。

第一版执行范围支持：固定十阶段、正常顺序推进、基于已记录事实和决定的条件分支、原模型声明的显式返工、等待判断及恢复。对不支持的行为表达给出诊断，不将其当作已执行。普通 `dependency` 用于工程含义和影响分析，不能直接触发动作。

检查前核对流程引用、阶段身份和规则适用范围。应用不执行规则文档中夹带的任务指令，也不因存在外部链接就自动取得新的工具能力；实际检查和任务通过已配置的工具入口执行。

### 4.2 阶段尝试 Attempt

一次阶段尝试把明确的输入和规则用于一次实际工作。它至少能定位：workflow 与阶段、尝试身份、wish 范围、工具版本、ConstraintSet、上游材料版本、工作主体和实际开始与结束情况。

开发资产仍可编辑。尝试开始后若需要改变它的输入或规则，应建立新的版本选择和尝试，不能改写原尝试已经采用的内容。约束演进不锁住整个开发周期；新的尝试可以显式采用新规则。

工作执行结果至少区分：已提交实际产物、执行失败、尚未完成，以及外部效果无法确认。收到 AI 文本、动作完成通知或工具退出码，不等价于已经提交了符合契约的产物。

### 4.3 阶段产物契约

每个阶段契约须能回答以下问题：

| 契约部分 | 应能判定的问题 |
| --- | --- |
| 输入 | 使用哪些 wish、上游工程元素、文件和实际证据版本？ |
| 允许工作 | 本阶段可以修改哪些工程范围，调用哪些已配置任务？ |
| 产物 | 需要提交什么模型、关系、文档、实现或证据，保存于哪些项目配置位置？ |
| 模型与 view | 哪些原生关系和 NativeView 必须新增或更新？ |
| 结构检查 | 哪些检查可执行，方法是什么，诊断定位到哪里？ |
| 工程语义 | AGENT 必须判断哪些问题，需要哪些支持材料？ |
| 出口 | 固定后续阶段或返工范围是什么，需要哪个关卡决定？ |

外部规范引用要选择确定内容及相关章节；其适用范围与版本进入 Candidate。无法读取的规范、未执行的检查和缺少的材料显式显示为缺口，不自动满足契约。

原 `ProducedBundle` 中所有类别至少一个的示例，不作为项目的统一硬编码产物数量。已有模型可以被本阶段引用和更新；是否需要新增模型或材料由契约决定。原生项目模型、独立 wish 链及其 view 的要求始终由相应模型契约核对。

## 5. 从产物到关卡

一次阶段工作按以下顺序交接：

1. 应用核对固定流程、WorkflowProfile 和当前上游选择，建立 Attempt。
2. 工作主体在允许范围内产生实际工程资产，提交文件和关系引用；项目仍使用自己的目录和版本管理。
3. 应用将待检查材料、ConstraintSet 和必要依赖固定为 Candidate，保留确定版本选择。
4. 语言工具和规则检查器对该 Candidate 产生 CheckResult；规则返回诊断和实际观察，不接受生产者自填“全部通过”代替检查。
5. 当前关卡的 AGENT 接收同一 Candidate、CheckResult 与语义评审问题，返回 Decision。决定有效性、用户调整及例外处理遵循 [gate.md](gate.md)。
6. 应用根据有效决定和固定流程选择下一阶段、返工、等待或停止，并保存实际采用的依据。

结构检查包含语法、类型与引用解析、必要原生关系、view、命名、位置及阶段允许产物。编译器称为 semantic validation 的类型和引用检查仍属于这一层。工程语义判断评价 wish、需求、设计、实现和证据是否充分、一致，不能由编译通过代替。

Candidate 在检查和决定前固定。后生成的 CheckResult 和 Decision 引用它，不回填 Candidate 内容并改变已审对象。改变所选工程内容或规则时形成新的 Candidate；尚未完成的旧判断可以作为历史返回，但不能不经核对就成为新材料上的有效决定。接入后来产生的事实引用不反向改变原 Candidate，也不单因记录接入推翻原工程判断；新增引用的结构另行核对，参见 [trace.md](trace.md)。

## 6. 推进、变更与返工

### 6.1 正常推进

运行应用每次调度都核对已知阶段及允许的后续边、Candidate 的适用性、上游依据和当前有效决定。关卡的完整推进条件由 [gate.md](gate.md) 统一规定，不在源模型中另写一套可以直接由产物生成者修改的通过布尔值。

工作范围可以覆盖已有项目的一部分，但不能把未处理的上游自动标为通过。复用既有设计或证据时，记录其确定版本、当前适用范围及真实检查和判断；不倒填历史阶段已经运行。每个阶段对本次范围如何完成或复用，必须有可解释的依据。

### 6.2 影响评估与返回

材料、规则或有效决定变化时：

1. 从实际采用的原生关系与版本引用找出受影响的 wish、阶段和决定。
2. 保留原事实，标明哪些旧决定不再适用于当前选择；无关范围不自动失效。
3. 评估最早受影响阶段，给出范围、原因及需要重新获得的依据。
4. 核对该目标属于固定流程允许的返回阶段，所需上游仍可使用，再建立新的 Attempt。

影响评估和返工所需的判断主体由本 workflow 明确安排。无法确定目标或缺少必要依据时等待补齐，不凭字符串猜一个阶段，也不自动批准返工。用户修改结果的决定保留其权威和历史；应用对后续动作的处理见 [gate.md](gate.md)。

V-model 包含回路，不能为实现方便把它转换成只允许无环的任务图。重复执行是新尝试，原失败日志、检查事实与决定继续保留；它不是覆盖原阶段记录。

### 6.3 等待与异常

| 情况 | 运行应用的处理 |
| --- | --- |
| 缺少 AGENT 分配或适用规则 | 定位配置缺口；不推断默认审批策略 |
| 产物位置未映射、材料无法读取 | 记录缺失范围，等待纠正或形成新的尝试 |
| 工具核心无法解释或固定流程引用不兼容 | 报告工具／流程诊断，不能假装完成执行 |
| 部分规则无法自动执行 | 保留未执行状态，按规则明确交给相应评审或补齐检查能力 |
| 判断尚未返回或工作被暂停 | 保留当前 Attempt 与 Candidate；恢复前核对是否仍适用 |
| 外部任务结果不确定 | 先核对实际效果，不能仅因没有收到响应就重复执行 |
| 拒绝、返工或用户改变结果 | 按有效 Decision 及其范围处理；事实和旧发布关联保持原内容 |

暂停、重复提交和恢复的持久化细节由 [storage.md](storage.md) 定义。

## 7. 与交付和后续生命周期的边界

`operationsHandover` 输出移交材料和确定工程范围，供 [release.md](release.md) 接入项目既有发布。阶段决定、实际产品发布和 ReleaseAssociation 是不同事实；它们分别记录真正发生的时间和依据。

新增 wish、运行反馈和约束调整进入后续开发，继续使用项目固定的 V-model。原模型中的 Wish 澄清、可行性、运行、演进和退役描述产品生命周期意图；本文不把这些说明自动转换成额外可定制的 V-model 拓扑或新的产品发布系统。

已确认发布的工程依据不被后来返工或用户调整覆盖。需要补充同一个实际发布的工程说明时，可以形成新的补充关联并保留旧关联，不强制重新发布产品，也不把新检查倒写成发布前证据。

## 8. 验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同一流程分别由人和 AI 担任 SRR | 阶段位置相同，Decision 有明确主体；没有隐含的人工或 AI 默认 |
| AI 提交模型并声称所有检查通过 | 应用仍产生真实 CheckResult，不能采信自填布尔值作为执行证据 |
| SysML 编译通过但需求不能解释 wish | 结构事实保留，关卡可判断返工；编译成功不自动放行 |
| 项目编辑约束后重做检查 | 新 Attempt／Candidate 使用新版本，旧检查和决定仍指向原版本 |
| 设计改变影响组件验证 | 原生关系定位受影响范围，返回固定阶段，新验证不覆盖旧结果 |
| 用户改变关卡结果 | 产生新的有效 Decision，自动检查事实和旧发布关联未改写 |
| 用户配置改动阶段顺序 | 配置诊断指出与固定 V-model 的差异，应用不执行自造拓扑 |
| 最后关卡通过但 CI 尚未发布 | 显示移交或待发布关联，不能宣称已有实际发布 |

这些是目标实现的验收要求，本次文档编写没有运行上述工作流或验证新的 SysML 源代码。
