# 工程资料与记录存储详细设计

状态：设计草案。日期：2026-10-13。依据：[架构设计](../arch_design.md)。本文定义可配置资料位置、确定版本的读写及保留行为；不规定数据库、强制目录树或另一套用户项目发布库。

## 1. 逻辑集合与维护来源

同一物理文件系统、Git 仓库或记录存储可以承载多个逻辑集合。逻辑集合用于解释维护职责和读写边界，不能由此要求项目创建同名目录。

| 逻辑集合 | 保存什么 | 维护与保留约定 |
| --- | --- | --- |
| 工具选择 | 已安装工具和固定语言、公共元模型、V-model、渲染及追溯机制的确定身份 | 接入时明确选择；普通工程编辑不更换选择，不在用户项目强制铺设工具版本目录 |
| 用户约束 | 原生约束 SysML、文档规范及外部规则选择 | 使用项目配置的位置和版本管理；修改形成新版本，历史检查继续选择原版本 |
| 工程资产 | 项目模型、各 wish 模型和 NativeView、文档、实现及验证计划 | 原生资料是工程内容及版本引用的维护来源；生成成果经保存后同样是持久工程资产 |
| 工作事实 | Attempt、CheckResult、Decision、用户新决定及实际证据 | 追加实际事实；当前决定可以选择新的记录，原记录不被覆盖 |
| Candidate 与发布关联 | 从原生选择确定的候选内容及依赖、ReleaseAssociation 记录 | 保留其确定内容和来源；不是可独立修改的模型副本或新的产品发布 |
| 派生缓存 | 解析表示、索引、预览及临时渲染 | 可从确定的工程资料和记录重建；不承担唯一保存职责 |

开发是可修改工程资料和追加工作事实的逻辑状态。发布关联固定既有实际项目发布的 MBSE 依据。用户项目的目录、产品发布身份与制品仍由项目原有工具维护。

## 2. 路径与现有工程接入

### 2.1 位置映射的内容契约

项目接入配置选择已有资料位置和适配方式，不自动移动或导入整个项目。

| 映射内容 | 必须说明的意思 |
| --- | --- |
| 项目资料根及来源 | 正在接入哪个工作区、仓库或文档系统，使用哪个已安装工具选择 |
| 原生模型位置 | 项目组成、wish 模型、共享定义和约束的已有位置及来源；相同资料只设一个写入来源 |
| 文档、实现与检查入口 | 当前工程采用的路径或受支持外部入口；哪些操作可由 xflow 请求执行 |
| 事实与证据位置 | 实际记录和必要证据保存在哪个持久位置，怎样读回确定版本 |
| 缓存位置 | 哪些位置可重建、可清除，避免把记录或未完成工作放入其清理范围 |
| 既有发布来源 | Git、CI 或制品系统怎样提供实际发布身份、源与制品版本及可读取的证据 |

路径既可以是已有仓库相对位置，也可以是所选适配器支持的外部资源定位。配置保存在用户选定的位置，不要求 `.xflow/`、`development/`、`releases/` 或工具版本命名目录。

例如，项目已经在 `architecture/` 保存模型、`notes/` 保存设计、`src/` 保存实现，可以直接映射这些已有位置。此例不成为默认目录或接入条件。新增 wish 文件保存在配置的原生资料位置，并保持其独立命名空间及 NativeView。

### 2.2 读取和写入范围

读写操作先解析项目映射，再解析所选资料或版本。普通读取不自动创建模型、记录、发布关联或替代文件。资料位置不存在、不可访问或来源不支持时，返回明确缺口，不能把它当作空项目初始化。

写操作具有明确目标、允许范围和预期原版本；不能因为接入一个仓库就任意重组整个仓库。外部 URI 通过所选适配器解析，不由 SysML namespace import 自动下载；不认识的定位方式保留为不支持的引用。

## 3. 确定版本引用

### 3.1 原生选择与实际观察

工程内容和版本引用以原生资料为权威。应用从经过解析的原生选择取得对象、关系、资料位置及预期版本，再核对实际读到的内容。记录保存本次采用的选择和实际观察；它不能提供一份与原生选择各自可编辑的替代清单。

| 选择对象 | 定位和核对所需的内容 |
| --- | --- |
| 原生模型 | 稳定工程身份、选定源文件版本与内容、原生端点及必要共享/语言依赖 |
| 文档或代码 | 来源、确定版本或可恢复的源快照、内容摘要；局部引用还包含该版本中的章节或范围 |
| 工作记录 | 原记录的确定身份、内容及所选 Candidate；显示摘要不替代原事实 |
| 外部资料 | 提供者与资源身份、确定版本、内容和必要定位；动态 URL 只作为寻找资源的线索 |
| 实际发布 | 既有发布系统的身份、实际源/制品选择及核对依据；显示版本名不是唯一版本证据 |
| 工具依赖 | 固定工具及语言库、公共定义和解释机制的确定身份，能够取得与其对应的内容 |

版本摘要核对实际字节或提供者可验证的确定内容。Git 分支、可移动 tag、文件路径、当前资源行和更新时间不能单独构成不可变选择。身份用于识别对象，摘要用于核对内容；相同字节不自动说明是同一个工程对象。

未提交的工程资料也可以参与开发检查，但需要保存当次实际内容，不能事后只用一个可能已变化的工作路径解释结果。保存历史来源不意味着自动提交 Git、推送仓库或发布产品。

### 3.2 Candidate 的保留

Candidate 是选定工程内容及依赖的确定集合。建立候选时，读取实际版本、核对完整依赖，并保存能够恢复该集合的选择和必要内容；随后检查及 Decision 只读取这个候选。

能够从现有版本管理恢复的内容留在原位置，保存确定引用。不能保证历史读取的材料，需要先在配置的持久位置保留必要内容。只保存一个 hash 而没有可读取的内容，不构成完整候选。

候选不包括它后来产生的 CheckResult、Decision、ReleaseAssociation 或自身摘要。记录的原生引用可能在后续模型版本加入，实际检查对象仍保持原 Candidate。详见 [追溯设计](trace.md)。

开发区后续编辑不改变已经确定的候选。若要让评审采用新内容，创建新的 Candidate 并记录替换范围；不能把旧选择暗中解析为最新版本。

## 4. 读取行为

一次确定版本读取依次完成来源解析、版本选择、内容取得及完整性核对，再返回工程内容或事实。引用读取要同时保留原生声明位置和实际资料来源，便于定位“声明了什么”与“读到了什么”。

| 读取方式 | 使用的选择 | 返回要求 |
| --- | --- | --- |
| 当前开发资料 | 当前明确选定的工程版本与约束 | 标明未提交、未经检查或引用不完整的部分，不借用旧通过结果 |
| Candidate | 已保留的确定选择及依赖 | 返回同一内容集合，不跟随工作区变更；无法恢复时报告缺口 |
| 原事实 | 实际保存的记录版本 | 保留实际时间、输入和观察；不存在时不从原生节点补造结果 |
| 发布关联 | 已确认 ReleaseAssociation 的工程选择及实际发布引用 | 按原选择读取，后续开发和用户决定不替换内部内容 |
| NativeView 展示 | 确定模型、原生 view 及所需事实引用 | 产生派生展示；缺失或不支持的选择明确可见 |

必须区分未配置、资料不存在、访问失败、内容不匹配、原生无法解析、解释能力不支持和历史版本无法恢复。它们可以形成可读诊断，不必为此建设通用状态码平台。

来源内容与预期摘要不匹配时，不能作为成功读取返回。历史模型解析失败时，保留源文本及诊断；缓存中的旧成功模型不得被重新标为当前结果。

## 5. 保存行为与不确定结果

### 5.1 工程资产保存

人或 AI 产出先成为可保留、可检查的候选材料。保存原生模型、NativeView 或文档时，操作读取当前版本，检查允许的修改范围，并以该预期版本提交。

保存至少保留：本次操作身份、输入候选、目标资料、预期原版本、实际结果及诊断。源适配器负责实现预期版本比较和完整写入；无法提供该能力时必须说明限制，不能宣称可防止覆盖。

并发编辑发生冲突时，保留当前原资料和待提交候选，重新组织修改。不能通过再读当前文件后静默覆盖别人的修改，也不能丢弃 AI 已经产生、尚待采纳的材料。

保存源文件与提交 Git 是两项行为；新增工作记录与保存源文件也可能是两项行为。它们分别记录结果，不能因为某一项成功就宣称整个工程修改已经完成。

### 5.2 工作事实追加

Attempt 在阶段工作开始前保留确定输入、规则和主体，其内可以包含多个实际执行或检查。CheckResult、Decision 及用户调整记录追加实际结果。当前有效决定是对这些事实的明确选择，更新它不覆盖原记录；用户未提供调整理由时如实标记，不以此新增全局门槛。

同一操作在回应丢失后重试，使用原操作身份及同一输入，查询或恢复原结果。已保存的事实不会因重复请求变成两次执行；同一操作身份不能接受不同输入。开展新的阶段工作时建立新的 Attempt；同一 Attempt 内确实新增的执行或检查另存实际记录，明确与前次执行的关系，不覆盖前次观察。

外部任务已发出但结果无法确认时，先保留不确定结果，核对任务、产物或外部回执。未知结果不能被当作已失败且安全重新执行。

### 5.3 跨资料与事实的交接

保存事实、接入原生引用、采纳工程资料和记录采纳结果可能跨不同来源。交接保留待完成操作和已经确认的结果，不承诺文件系统、Git、外部发布系统与记录存储共享一个事务。

| 中断位置 | 恢复行为 |
| --- | --- |
| 候选已保存，工程源尚未更新 | 读回候选和预期版本，重新核对后继续保存或报告冲突 |
| 工程源已写，回应或记录尚未确认 | 读回实际目标版本并核对本次内容，再恢复原操作结果；不再盲写一遍 |
| 事实已保存，原生引用接入失败 | 保留事实及待接入信息，用原记录恢复引用，不重新执行任务 |
| 发布关联尚未确认 | 保留候选和核对结果，显示未完成；不能暴露为已确认关联 |

未完成编辑、已封存输入和需要恢复的候选都持久保存。缓存清理不能清除这些内容。具体保存介质可由同一物理存储承载，不需要另设一套项目管理服务。

## 6. 不可变发布关联的保留

实际产品发布继续由项目现有 Git、CI 或制品系统完成。xflow 保存 ReleaseAssociation，连接实际发布身份与确定的模型、约束、关系、检查及 Decision；它不创建平行产品发布编号或要求复制产品 payload。

确认前核对实际发布内容与 Candidate 中有关实现、验证和工程范围的选择。只有 AGENT 判断或一个显示 tag，不能代替外部系统实际发布结果。详见 [发布设计](release.md)。

关联及其选定依据确认后保持不可变。资料可以继续留在原 Git、制品库或能够保存确定内容的证据存储；多个关联可以引用同一份已保留内容。对不足以保留版本的来源，保存必要 MBSE 依据，而非默认复制整套产品制品。

确认后新增 wish 原生发布引用时，保存新的模型版本并指向已有真实关联，不修改该关联的依据快照，也不倒插到原 Candidate 中。记录接入的结构检查可以独立选择进入后续依据，不要求为了包含自身检查或关联而不断重写、重新封存旧内容。

同一实际发布允许新增修正或补充关联，明确所补依据及先前关联。旧关联仍可读取，补充工作保留真实发生时间。产品内容确实改变时，继续使用项目既有发布流程。

读取时核对确定引用。外部内容被更改、删除或变得不可读取时，保留原关联并新增可用性或损坏诊断；不能把最新文件替换成原发布依据。需要保存的依赖不能仅因为当前开发已不引用它而清理。

工具版本使用项目选定的安装或发行方式保留，不强制用户项目建立工具发布目录。旧依赖不可取得时，不能用新工具悄悄替换后声称复现了原检查；原记录及材料仍保持可读，无法执行的部分明确说明。

## 7. 资料增长、索引与缓存

项目资料持续增长包括新增 wish、模型修订、文档、实际尝试和证据，不意味着每次检查都载入全部历史，也不意味着每份工程文件只能追加而不能修订。

### 7.1 范围读取

- wish 工作读取其原生链、选定项目元素及必要共享依赖。
- 项目组成读取模型声明的部件和行为；进一步追溯按明确的关系展开。
- Candidate 和发布关联读取其固定依赖，不把全部失败草稿和无关历史拼入评审材料。
- 历史事实按目标、候选及时间查询；需要某条原事实时才读完整内容。

语言检查仍要加载所选范围的完整语义依赖。减少展示和评审输入不允许省略实际编译需要的定义，或把分页面外端点当成不存在。

### 7.2 可重建索引

索引只缓存从原生资料及事实读出的稳定身份、源版本、类型、关系端点、记录定位和依赖。它不能单独写入新的工程关系或版本选择。缓存键绑定来源内容及相关工具解释版本。

资料变化后，更新或重建受影响源及依赖的索引。无法确定增量影响时，回到确定范围重新解析；不能拿部分旧索引宣称当前链完整。外部编辑同样通过实际版本核对识别，不仅依赖 xflow 自己发出的修改通知。

分页和范围限制返回明确范围、是否省略及继续读取方式。范围外、已省略和无法解析分别显示。查询结果不能混合不同 Candidate 或发布关联的选择。

### 7.3 保留与清理

解析表示、查询索引和临时图片可以丢弃。工程源、事实、证据、待恢复候选及已确认关联依赖不能依靠缓存保留。

相同不可变内容可以复用，稳定引用仍区分不同工程身份。历史开发资料可以归档到仍可读取的位置；本设计不引入通用内容目录、跨项目资源平台或自动破坏性清理机制。

## 8. 验收例

| 场景 | 应观察到的结果 |
| --- | --- |
| 已有项目使用自己的模型、文档和源码目录 | 按配置读写，目录和发布流水线不迁移，不生成强制工具/项目发布目录 |
| 工程模型和事实存于同一物理存储 | 逻辑维护来源仍明确，工程源与追加事实各自遵守读写契约 |
| 生成模型和文档后清除缓存 | 原生模型、NativeView、文档、事实和证据仍可读，展示可以重建 |
| 两个 wish 同时修改共享部件 | 预期版本冲突被报告，原资料和待提交候选均保留，不静默覆盖 |
| 检查前保存工作区候选，随后编辑工作文件 | CheckResult 仍能恢复其实际 Candidate；不把新文件当作旧输入 |
| 记录保存成功但回应丢失 | 同一操作读回原事实，无重复执行、重复决定或第二次发布关联 |
| 外部任务可能已经执行 | 保留不确定结果并核对效果，不能直接换一个身份再次派发 |
| 现有发布系统交付项目版本 | xflow 只关联实际身份及确定 MBSE 依据，不另发一个产品版本或复制 payload |
| 旧关联的外部依赖被删除 | 关联原内容不变，缺失明确可见；有保留内容时可恢复，无保留时不冒称复现 |
| 一个项目累积大量 wish 和历史记录 | 当前工作按范围与依赖读取，索引可重建，省略信息不伪造成关系缺失 |
