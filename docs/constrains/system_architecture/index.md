# 系统架构与方案：文档组织及设计规范

规则集版本：0.1。状态：目标约束草案。日期：2026-10-12。

本目标对应 `systemArchitecture` / `ArchitectureSpec`，关卡为 PDR。依据[整体架构 0.2](../../../design/workflow_mbse_architecture.md)与[公共规范](../README.md)。检查使用[语法规则](syntactic_constrains.md)，工程充分性使用[语义规则](semantic_constrains.md)。本文件规定新增架构产物的表达方式，不证明现有设计已获批准。

## 位置与命名

架构材料属于开发资产，参考位置为 `development/docs/`，原生组成与行为模型为 `development/models/`，验证入口在契约登记的开发位置。现有 `design/`、`models/` 等可通过契约映射保留；此目录仅保存约束规范。发布后对应文件和 view 冻结，只读访问。

| 产物 | 文件名规则 | 必须表达的内容 |
| --- | --- | --- |
| 总体架构 | `<scope>_architecture.md` | 目标边界、方案、组成行为、模块接口、部署/运行、信息归属、验证与风险 |
| 方案比较 | `<scope>_trade_study.md` | 候选方案、约束、比较依据、取舍、选定理由 |
| 接口规范 | `<scope>_interfaces.md` | 稳定接口身份、两端责任、数据/控制方向、正常及失败语义 |
| 集成计划 | `<scope>_integration_plan.md` | 集成单元、顺序、配置、环境、用例与架构/接口覆盖 |
| 决策说明（需要独立维护时） | `<scope>_architecture_decisions.md` | 问题、备选、证据、选择、后果和依赖 |
| 原生模型 | `<scope>.sysml` | 对应命名空间、部件/端口/接口/行为、关系、原生 view usage |

`<scope>` 使用稳定而明确的系统或子系统名称，小写英文与下划线；版本保存在文档元信息和基线选择中，避免以 `final`、`latest` 或 `v2_final` 代替版本管理。例如现有 `design/workflow_mbse_architecture.md` 可以作为总体架构入口。

允许把方案、接口和集成计划合并为架构文档的稳定章节；产物清单要映射其类型、身份、文件版本与章节。拆分后主文档链接所有子文档及其所属模型，不按每条 Wish 复制共享架构。

## 总体架构的必需内容

1. 文档身份、范围、版本、草案/候选/采纳状态、Wish 与系统需求基线、流程及规则选择。
2. 系统目标、边界、外部参与者、主要使用场景、假设和限制；区分当前能力、目标能力及后续扩展。
3. 候选方案、关键约束、选定方案和依据；只有一个候选时解释为何其他方向不适用。
4. 原生项目组成与行为、模块职责和边界、依赖方向、需求分配与满足关系。
5. 关键接口、主要工作流和状态变化，包含失败、取消、返工及恢复的交接；系统外部效果和控制责任可识别。
6. 固定工具机制、可变用户约束/工程资产、累积记录与缓存的归属，稳定身份、版本、采纳和变更影响。
7. 本地进程/模块与部署边界、资源约束、复用依赖及执行 profile；独立部署需要工程依据。
8. 候选内容选择、发布检查与决定、核对/封存、只读访问、依赖保留与损坏诊断，以及集成计划、架构验证、风险和下一阶段范围。

标题可以依项目调整，但以上内容都需通过章节映射可定位。检查器校验存在与关联，AGENT 判断内容是否适合需求。

## 设计表达

以 SysML 原生模型承担组成、接口、行为与追溯身份；文档解释设计理由、边界和取舍，图表引用同一元素身份。Mermaid 或图片的箭头标明组成、依赖、执行顺序或数据流含义，不能用一张图替代原生 view 或满足关系。

接口描述至少说明身份、提供方/使用方、输入/输出、前置条件、可观察效果、失败行为及版本依赖；具体序列化字段和 API 在详细设计展开。每个模块说明负责的状态与数据、调用边界、对其他模块的依赖和应提供的可检查输出。

针对当前产品，要明确项目初始化、阶段执行、编译与结构检查、AGENT 关卡、追溯维护、渲染查询和项目发布的职责与写入边界。适配器、协调器、工作台和存储可按实现需要分工，初期可同进程部署；现有 xdesign/Pilot 的复用边界及待建设能力必须有依据。

工具版本 T1 与固定依赖由初始化绑定，整个项目的 V-model、公共元模型、解析、渲染和追溯机制固定。用户规则 SysML 经公开扩展接口演进，项目模型/view 内容可以增长。发布是创建新对象：候选内容标识与最终决定分离，旧 R1 不因开发修改、规则换版、用户改决定或发布 R2 而变化。工具项目的候选机制经验证后交付 T2，不替换正在执行的 T1。

架构验证必须说明 R1→继续开发→R2 的隔离场景、旧发布使用原工具读取、只读保存拒绝、外部修改损坏诊断，以及共享不可变依赖保留。按[发布目标](../project_release/syntactic_constrains.md)展开发布准备与封存，不额外移动 V-model 关卡。

设计中使用“必须”“允许”“建议”区分约束强度；未知内容写明假设与影响。架构主张需关联需求、设计元素和预定验证方法；PDR 评价方案适合性，CDR 再评价展开后的组件设计。

## 提交审查

提交实际文档、原生模型及 view、方案/接口/集成计划的章节映射、追溯关系、结构诊断和问题清单，固定版本形成 PDR 审查包。通过、返工及例外决定按[公共协议](../README.md)保存；文档自身不能预设审查结果。
