# 系统架构与方案：语法校验规则

规则集版本：0.1。状态：目标约束草案。日期：2026-10-12。

## 适用范围、输入与产出

对应 `VModelDevelopment::systemArchitecture`、`ArchitectureSpec/ArchitectureBundle` 和 PDR。依据[整体架构 0.2](../../../design/workflow_mbse_architecture.md)、[产物定义](../../../wish_to_product.sysml)。先遵循[index](index.md)、[模型规则](../model_traceability/syntactic_constrains.md)和[运行规则](../workflow_execution/syntactic_constrains.md)。本规范不表示检查器已实现。

输入为当前 Wish、SRR 的选定需求与系统验证计划、可行性材料、项目模型、项目固定工具/流程及用户规则版本。允许在开发区比较方案、设计组成/接口/行为、分配需求、制定集成计划与更新追溯/view；旧发布只读。不得把后续实现或验证声明为已发生。

## 规则

| ID | 约束与判定方法 | 诊断位置 |
| --- | --- | --- |
| ARCH-SYN-001 | 审查选择包含 Wish/增量/尝试、需求基线、SRR 决定、可行性材料、流程和规则版本；产物来源与该选择一致。 | 输入清单、基线与尝试 |
| ARCH-SYN-002 | 实际架构文档与子文档满足 index 的命名和内容映射；合并文件时方案、接口、集成计划各有稳定章节定位。必需内容不能仅为占位标题。 | 文件名、文档元信息、章节映射 |
| ARCH-SYN-003 | 架构模型能在选定源集合与库上解析，声明项目部件、端口/接口及关键行为；定义和具体 usage 及其来源身份可区分。 | `.sysml`、元素限定名、工具诊断 |
| ARCH-SYN-004 | 本范围每条系统需求有分配/满足端点，或明确的待分配问题记录及影响；原生 satisfy/适用 allocation 合法，其他关系有角色定义。缺口不能用空关系占位隐藏。 | 需求覆盖、原生关系、问题清单 |
| ARCH-SYN-005 | 职责清单注明读取/写入边界、输入输出及依赖；对本产品初始化、阶段执行、检查、AGENT、追溯、渲染查询与发布分别有设计元素或明确合并映射。 | 职责说明、项目模型、区域映射 |
| ARCH-SYN-006 | 接口有稳定身份、提供方/使用方、方向、类型或协议、前置条件、效果与失败说明；连接端点可解析，声明的方向/类型能进行一致性检查。 | 接口表、port/interface、连接关系 |
| ARCH-SYN-007 | 候选方案和选定方案能定位，比较维度关联需求/约束及依据；单方案附其他方向不适用说明。 | 方案比较、架构决策 |
| ARCH-SYN-008 | 正常流程及关键异常流程有参与部件、交接、状态和出口表达；执行顺序用适用行为关系，追溯 dependency 不用于跳转。 | 行为模型、状态/顺序图 |
| ARCH-SYN-009 | 信息清单区分固定工具、可变约束/开发资产、原事实/新记录、缓存与不可变发布，映射 Git/ProjectStore 等来源；说明身份、版本、引用和变更入口，不建立重复事实来源。 | 信息归属表、区域读写、引用绑定 |
| ARCH-SYN-010 | 集成计划列出集成单元、顺序、依赖配置、环境、预定用例、通过判据和架构/接口覆盖关系；未执行计划不能填写为实际结果。 | 集成计划、预定用例、关系 |
| ARCH-SYN-011 | 架构及相关 Wish 模型具有本阶段原生 view，能解析选定需求、部件、接口及关系；风险、假设、复用与待建设边界有可定位记录。 | view、风险和边界说明 |
| ARCH-SYN-012 | PDR 审查包固定本次模型、文档、关系、规则、诊断和问题；有效决定只能准许选定的 `detailedDesign`，发生相关变更重新组织审查。 | PDR 包、决定、下一工作 |
| ARCH-SYN-013 | 工具绑定及固定依赖、用户约束 SysML 的扩展方式、机制与模型内容的差别可定位；规则换版不修改 V-model/公共元模型/编译渲染追溯机制。 | 工具/规则架构、初始化及扩展接口 |
| ARCH-SYN-014 | 发布架构说明范围及依赖选择、候选内容标识、检查/发布决定、核对、封存新身份、只读读取与损坏诊断；候选标识不循环包含最终决定，准备失败无成功发布对象。 | 发布流程、清单/候选/决定关系 |

## 出口与返工

保存实际检查结果后执行[语义评审](semantic_constrains.md)。通常产物齐备且当前 PDR 决定有效才进入详细设计；用户替代决定按公共协议限定例外范围，原缺口保持原结果。缺失需求依据回系统需求，结构/接口或计划缺口在架构阶段新尝试修复；无法解释的模型先修复语言及引用问题。

## 判定示例

结构合格：架构文档映射 `coordinator` 与 `record_store`，接口注明双方和失败输出，集成计划关联接口身份，模型有原生 view 并记录所用 SRR 基线。

结构不合格：只有“工作台→AI→完成”的图片，没有部件、接口或集成计划；或以一条自定义 dependency 声称需求满足，却没有定义其角色。
