# 详细设计：文档组织及设计规范

规则集版本：0.1。状态：目标约束草案。日期：2026-10-12。

本目标对应 `detailedDesign` / `DesignSpec`，关卡为 CDR。以[当前整体架构 0.2](../../../design/workflow_mbse_architecture.md)和选定 PDR 材料为依据，遵循[公共规范](../README.md)。[语法规则](syntactic_constrains.md)检查表达和结构，[语义规则](semantic_constrains.md)判断是否足以实现与验证。架构的职责在本阶段展开为具体契约与行为。

## 位置与命名

详细设计及组件模型/验证规程属于开发资产，参考位置为 `development/docs/`、`development/models/` 及契约登记的验证入口。现有 `design/` 等可映射保留；已发布对应文件不可原位编辑，需在开发区建立新版本。

| 产物 | 文件名规则 | 必需内容 |
| --- | --- | --- |
| 组件详细设计 | `<component>_detailed_design.md` | 职责、结构、接口、数据/状态、算法与错误、依赖、追溯、验证准备 |
| 组件规范（独立时） | `<component>_specification.md` | 输入输出、前后条件、不变量、异常和资源约束 |
| 数据/记录规范（独立时） | `<component>_record_schema.md` | 身份、字段类型、版本、引用、归属和演进 |
| 组件验证规程 | `<component>_verification_cases.md` | 用例身份、设计端点、环境、步骤、预期与通过判据 |
| 主设计入口（多组件时） | `<scope>_detailed_design.md` | 组件清单、子文档/模型映射、共享约束及依赖 |
| 组件原生模型 | `<component>.sysml` | 结构、行为、约束、验证用例与原生 view usage |

名称使用稳定组件或范围的小写英文与下划线。版本通过元信息和审查基线管理，避免“最新稿”等名称。允许合并规范与验证规程为稳定章节，但提交清单需定位各类内容。组件身份保持与架构一致；重命名、拆分或合并要有映射及影响说明。

## 必需设计表达

组件文档先列身份、版本、状态、范围、所属 Wish、上游架构/接口与需求基线，再说明责任和依赖。正文覆盖以下内容，章节可按具体组件合并：

1. **组件结构**：内部职责、实际配置和外部依赖，引用对应原生元素。
2. **接口契约**：操作/事件身份、输入输出和类型、前置/后置条件、失败结果、调用及取消语义。
3. **数据与记录**：字段/关系的类型与必需性、稳定身份、版本、唯一来源、持久化及引用定位。若无持久数据，说明原因。
4. **行为与算法**：正常路径、分支条件、状态变化与允许出口；排序、并发、去重、超时和重试在有相关行为时展开，不给无关组件强加机制。
5. **一致性与异常**：不变量、冲突、部分成功、不确定外部效果、恢复点和补偿/返工责任。
6. **约束与取舍**：资源、性能、支持 profile、依赖库/工具版本、实现选项及依据。
7. **工程追溯**：需求、架构元素、接口及具体设计元素的对应，尚未实现的引用保留计划含义。
8. **组件验证准备**：设计主张、边界和失败路径对应的用例、环境、步骤、预期、通过判据及所需证据；本阶段不产生未来执行成功事实。
9. **未解决问题**：缺口、影响、责任、处置和下游限制。

数据表和伪代码可以解释设计，必须注明其规范性与适用版本；伪代码不能声称可被当前执行器直接运行。图表与正文共享元素身份，箭头语义明确；状态图每个出口对应已解释条件。

## 当前产品需要展开的子设计

对初始化说明工具发布/固定依赖绑定与开发区建立；对协调器说明阶段尝试、分支/返工、暂停取消和恢复；对语义适配器说明按项目绑定加载、身份/诊断与支持 profile；对追溯服务说明固定关系机制与可变关系内容、共享身份、view 和章节定位。

对检查器说明规则绑定、输入选择和结果协议；对 AGENT/执行适配器说明主体、授权、审查包/工作契约与输出；对存储说明实际记录、版本检查、采纳交接、历史内容恢复及去重；工作台说明这些事实和有效决定如何被正确展示。每项只在负责组件中维护一个定义来源。

对发布职责说明候选身份与内容摘要、依赖闭包、最终决定引用候选、核对与封存、失败恢复、不可变发布路径与访问控制、读取校验及包内渲染文件保护。旧发布引用的共享内容不可被开发编辑或清理覆盖；撤回说明在对象之外追加。工具项目中的候选 V-model/工具代码不改变当前执行 T1。

组件验证规程按设计责任覆盖工具绑定核对、用户约束换版、开发写入、旧发布保存拒绝、候选变动重新审查、封存失败无虚假成功、损坏诊断和只读继承。集成/系统验证再检查完整 R1→开发修改→R2 场景及原工具读取。

## 提交审查

CDR 材料固定组件模型、详细设计/接口/记录规范、验证规程、追溯和 view、实际结构结果及问题清单。设计必须足以让实现者生产受控组件并让验证者检验设计符合性；若需要修改架构边界，先记录影响并返回架构审查。CDR 不代替构建或组件验证的实际结果。
