# 系统验证阶段的语义约束

规则集版本：0.1。日期：2026-10-12。状态：目标约束。

适用架构：[整体架构 0.2](../../../design/workflow_mbse_architecture.md)。项目初始化绑定工具发布 `T1` 及固定依赖：V-model、公共元模型、编译/解析、渲染和追溯机制在项目生命周期内保持不变，工具升级另行迁移。用户语法/阶段约束 SysML、语义评审约束 SysML、文档规范及外部规则可以发布新版本，新尝试显式采用；既有证据和决定保留原选择。

## 适用范围及依据

本规则判断实际集成系统的证据是否充分支持选定系统需求的满足，关卡为 `System verification review`，后续工作是使用确认与验收。符合系统需求的判断与“满足 wish 的预期用途”及验收判断分别进行。语义充分性由该 workflow 配置的人或 AI AGENT 判断；检查通过不能替代有效关卡决定，也不宣称规则已有自动实现。

依据：[整体架构设计](../../../design/workflow_mbse_architecture.md)（0.2）的“用户约束如何演进”“一次发布的执行过程”“最小可执行范围”，[V-model 定义](../../../v_model_agents.sysml)的 `SystemVerificationAgentBehavior`、`systemVerifiesRequirements` 和 `ValidationAgentBehavior`，以及 [Wish 生命周期模型](../../../wish_to_product.sysml)的 `SystemVerificationSpec`、`ValidationSpec` 和验证阶段输入关系。

通用要求见[路由说明](../README.md)、[模型与追溯语义约束](../model_traceability/semantic_constrains.md)、[工作流执行语义约束](../workflow_execution/semantic_constrains.md)；机械结构要求见[本阶段语法约束](syntactic_constrains.md)。

## 输入、允许工作与产出

评审和用户替代决定形成新的开发记录；不回写旧发布。纳入后续发布的早期证据保留其真正检查输入、上游模型、实现和规则版本，AGENT 评价它对当前选择的适用性，不能重标为针对最终内容重新执行。相关要求见[项目发布语义约束](../project_release/semantic_constrains.md)。

评审输入为同一版本选择下的系统需求及计划、当前集成系统和集成验证限制、实际方法及执行证据、环境/负载/数据、需求覆盖与缺口、异常及处置、检查结果和变更影响。

允许评价需求满足、复核测试和分析、识别判据及环境问题、要求复验或补充证据、提出需求/设计/实现等返工。产出是逐需求的证据充分性评价、系统验证报告及 `System verification review` 决定，说明对使用确认移交的系统范围、已知问题和适用限制。

## 规则表

| ID | 约束判定 | 评审证据 |
| --- | --- | --- |
| SV-SEM-001 | 被验证对象应是本次实际集成系统，需求属于当前 wish/增量选定范围。历史构建、局部组件或配置不同的系统，其结果仅在差异及适用性论证后用于明确范围。 | 系统/集成清单、需求基线、wish 追溯、版本差异与复用依据。 |
| SV-SEM-002 | 满足主张需要实际测试、分析、检查或演示的结果支持。需求被模型 `satisfy`/`verify` 引用、计划存在、编译成功或集成关卡通过，不足以证明系统需求已经满足。 | 原始观测、计算输入/输出、检查记录、实际方法与执行记录。 |
| SV-SEM-003 | 所选方法及判据能判断需求的量化阈值、条件与容差，或对定性要求提供可复核判断。分析假设、模型有效性和计算方法需要说明；不得以实现输出或事后调整阈值作唯一判据。 | 需求判据、方法选择、分析假设及验证、独立预期依据。 |
| SV-SEM-004 | 需求覆盖应包括当前范围的功能、性能、可靠性及其他适用约束，覆盖选定运行条件和边界。每项缺口说明风险及后续安排；“全部已执行用例通过”或单一覆盖百分比不能证明全部需求满足。 | 逐需求评价、条件/边界覆盖、缺口与风险、未执行项说明。 |
| SV-SEM-005 | 实际环境、负载、输入数据和测量能力应足以代表需求的适用条件。简化环境、仿真或替代件的偏差与测量误差纳入结论；临界结果应考虑精度，不得扩大支持范围。 | 环境对照、代表性论证、数据与负载来源、精度/误差分析。 |
| SV-SEM-006 | 每项满足结论应由实际观察与需求判据一致地支持。未知结果、中断、日志缺失、未执行和无法解释的波动保留不确定性；不适用项的排除有当前需求范围依据。 | 观察与判据比较、未知项核对、波动分析、不适用依据。 |
| SV-SEM-007 | 需求间相互影响及系统级组合行为应被考虑，局部通过不能掩盖共同运行下的资源、时序、故障或约束冲突。必要时增加组合场景及回归，解释系统结果与组件/集成结果的差异。 | 需求交互、系统场景、资源/时序记录、跨层证据差异与回归。 |
| SV-SEM-008 | 所有失败和异常的处置应可信地关闭对应需求不符合，修复后复验及必要回归覆盖受影响范围。重复执行直到偶然通过、删掉失败或将问题改名，不构成闭环。 | 原始失败、根因、修订、逐需求复验与回归、处置理由。 |
| SV-SEM-009 | 需求、架构、实现、配置、依赖、方法和环境变化应触发相应证据适用性评价；选择必要复验及最早受影响返工阶段；复用时保留证据的真正输入/规则和原支持范围，不把早期执行重标为针对最终内容执行。共享系统证据服务多条 wish 时，每条 wish 的支持范围分别明确。 | 变更差异、依赖与追溯、证据失效/复用范围、复验及返工选择。 |
| SV-SEM-010 | 遗留需求不符合、覆盖缺口和残余风险应向使用确认移交，AGENT 说明它们是否阻塞后续工作。例外须依据 workflow 授权记录范围、限制与处置；有效许可不能将未满足需求改写为已满足。 | 问题分级、残余风险、后续验证/确认前提、例外及当前有效决定。 |
| SV-SEM-011 | `System verification review` 的理由与选定审查包一致，明确哪些系统需求在何种条件下得到支持，并说明是否允许 `stakeholderValidation`。该决定不能直接宣称预期用途已获确认、验收完成或 wish 完成；用户修改决定新增开发记录，保留真实观察及不确定性，不回写旧发布。 | 逐需求语义评价、决定与证据、使用确认移交范围、替代决定历史。 |
| SV-SEM-012 | 当前系统需求规定的发布隔离应由实际 R1→开发修改→R2 场景支持：T1 及固定依赖保持相同，规则/模型/文档/用户决定的修改只进入开发与新发布，R1 的内容、决定和依赖选择完全不变，仍能用原 T1 读取及展示。早期证据的原输入/规则可恢复并有适用性判断，新增 wish/共享资产不复制工具内核或覆盖原成果；该结论仍不替代预期用途确认。 | 发布前后摘要/清单、规则与决定历史、原 T1 读取/渲染、共享资产记录及需求判据。 |

## 出口与返工

AGENT 对选定系统范围记录待判断、通过、返工或拒绝的结论及理由。协调器使用当前有效 `System verification review` 决定、产物契约和运行前提允许使用确认；后续 Acceptance review 仍根据预期用途、场景和验收材料作独立判断。

证据或方法不足时补充系统验证；实现、架构、需求或集成问题按影响评估返回相应流程阶段。返工保留原始失败及原决定，新尝试形成新的证据选择。用户修改决定只能替代有效结论及允许后续范围，不能补出未执行事实。

## 例子

合格：系统需求规定在选定负载下告警时延不超过阈值。实际集成构建的多次边界及故障恢复运行留有原始时间数据，精度足以判定，首次失败经修复、复验和回归闭环。AGENT 逐需求解释支持范围及已知限制，允许进入使用确认，仍要求使用场景证明告警对种植者的预期价值。

不合格：实验室空载系统满足性能阈值，便宣称生产负载性能、用户体验及验收全部通过；生产负载测试未执行且日志缺失。违反 SV-SEM-004、005、006、011，系统验证结构合法也无法支持这些结论。
