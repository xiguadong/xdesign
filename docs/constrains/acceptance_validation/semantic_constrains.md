# 使用确认与验收的语义充分性约束

规则集版本：0.1。日期：2026-10-12。状态：目标规范；评审要求不表示已有验收结果或自动语义检查实现。

## 适用范围、依据与输入

适用于 `stakeholderValidation` 的 `Acceptance review`。依据[整体架构设计 0.2](../../../design/workflow_mbse_architecture.md)、[V-model 的确认职责与关卡](../../../v_model_agents.sysml)和[生命周期模型的 ValidationSpec](../../../wish_to_product.sysml)。输入为同一选定审查包中的 wish 意图、利益相关方需求、完成契约、产品版本、系统验证结果、确认场景、实际使用证据、剩余问题及适用规则。通用评审方式见[模型与追溯语义约束](../model_traceability/semantic_constrains.md)、[运行语义约束](../workflow_execution/semantic_constrains.md)与[目录总说明](../README.md)。

本阶段询问产品在预期使用条件下是否实现 wish。系统验证回答产品是否符合系统需求，两种主张分别保存；系统验证结果是输入证据之一。配置的人或 AI AGENT 判断本阶段充分性，并记录理由、反例、未满足项与不确定性。工具统计或检查通过只提供事实。

## 允许工作与产出

允许评价确认计划的代表性、执行结果的适用性、用户反馈、残余风险与验收条件，形成可归属的验收结论和逐 wish 完成建议，并将新评审和决定保存到开发区。允许提出补充确认、限定使用范围或返工；不能为方便放行而在本阶段静默重写原意、验收阈值或上游基线，也不能改变旧发布中的判断。语义评审输出须链接具体证据和判断范围，文件结构遵循[本阶段语法约束](syntactic_constrains.md)。

## 规则

| ID | 约束判定 | 诊断位置或评审证据 |
| --- | --- | --- |
| AC-SEM-001 | AGENT 逐 wish 判断使用确认是否覆盖原始意图、预期结果和验收意图；后续细化与原意有差异时说明差异是否获得明确变更决定。满足派生需求而未实现预期用途不能得出验收充分。 | wish 来源、澄清记录、用途到场景映射和逐 wish 判断理由。 |
| AC-SEM-002 | 场景应代表目标用户、实际环境、操作频度、关键异常及约束条件；AGENT 解释选取与遗漏，判断被省略条件是否可能改变结论。仅在理想环境中的演示不能自然外推到全部使用范围。 | 确认计划、环境差异、场景选择理由及缺口分析。 |
| AC-SEM-003 | 评价指标和接受边界足以判断用户实际成果，且在评价中没有事后降低阈值或更换统计口径；主观满意度和客观观察各自说明依据，结论应能解释边界场景与反例。 | 原定验收标准、实际结果、评价方法和变更记录。 |
| AC-SEM-004 | AGENT 判断证据与待交付产品配置一致，使用者、运行方式、数据和依赖差异在可接受范围内；对替代环境、模拟、样本量或未执行场景说明其限制，并限制结论范围。 | 产品基线、配置差异、原始操作记录及证据适用性说明。 |
| AC-SEM-005 | 系统验证与使用确认的证据组合应分别支持需求符合性和用途满足性；AGENT 检查通过的系统需求是否遗漏了用户目标，确认演示是否掩盖系统验证失败。两类缺口均须有明确处置。 | 系统验证包、确认报告、覆盖差异及未决项处置。 |
| AC-SEM-006 | 利益相关方反馈应来自与本 wish 有关的角色或可解释的代表；AGENT 判断冲突意见、未参与角色及评价偏差是否影响验收。判断者可以是配置的人或 AI，不能把 AI 生成的赞同文本当作真实用户反馈。 | 参与角色说明、原始反馈、冲突处理及代表性理由。 |
| AC-SEM-007 | 剩余问题和风险按具体使用影响评估，说明限制、缓解措施、责任主体和再评价条件；AGENT 判断这些条件是否实际可执行。具有例外的接受结论须给出范围，不能笼统接受全部未知风险。 | 问题清单、风险依据、使用限制与明确的接受理由。 |
| AC-SEM-008 | 一个增量覆盖多条 wish 时，AGENT 分别判断完成契约要求的路径与证据是否充分，共享证据只在可说明的范围内复用；每条 wish 的完成、部分完成或待补充理由独立保存。 | 各 wish 的完成选择、共享证据适用范围及完成决定。 |
| AC-SEM-009 | 进入 `operationsHandover` 的结论应说明接收范围、仍需完成的移交工作和允许行为；按完成契约判断移交是否属于 wish 完成。验收通过不自动推出已交付、已运行或 wish 已完成。 | `Acceptance review` 理由、完成契约、移交边界和下一项工作。 |
| AC-SEM-010 | 用户修改结果后，AGENT 或协调器仍应呈现原失败事实、未执行检查和历史决定；判断例外是否只影响明确规则与范围，并评估对下游结论的影响。用户结果不能使缺失证据或不可用调度前提变成真实存在。 | 用户新决定、例外边界、原始检查和依赖影响分析。 |
| AC-SEM-011 | 显式采用新约束重新验收时，AGENT 判断它改变了哪些评价标准及证据适用范围，形成新的开发判断；初始化固定 T1 的工具依赖、关卡和追溯机制不随之变化。旧证据保留其原输入和规则，不能将早期检查解释为按新标准或最终产品重新执行。 | 工具绑定、约束差异、旧证据范围、复评理由与新决定。 |
| AC-SEM-012 | 对从 R1 继承的产品重新评价时，AGENT 分清 R1 原有验收主张与本次开发结论；新发现或用户替代决定只改变当前开发适用性。需要撤回、替代或发布新结论时，说明保存在原对象外或进入新发布，不能改写 R1 证据与完成历史。 | 继承范围、开发评审、外部撤回说明与发布边界。 |

## 出口与返工

通过结论应说明为何这些证据足以支持本次预期用途、哪些限制仍适用、允许何种移交工作。待判断、返工、拒绝和当前选择已失效的结论分别保留；满足源模型的放行条件后才进入 `operationsHandover`。语义证据不足时补充确认；若问题涉及原意、需求、设计或实现，进入影响分析并回到最早受影响阶段建立新尝试，重新评价相关下游决定。

完成 AGENT 依据完成契约作逐 wish 决定，不由运行结束或验收包声明推定。对明确范围的用户例外，保存新有效决定并按选定流程/profile 重新计算可继续性，实际调度前提保持真实。

## 示例

合格：系统验证表明需求得到满足，但 AGENT 仍要求目标用户完成关键使用场景；实际结果支持预期成果，遗漏的低频场景形成有限使用范围与后续复核条件，逐 wish 记录验收和完成边界。

不合格：所有自动测试通过，AGENT 据此认定“用户一定满意”，忽略真实使用中仍需手工绕过核心步骤的反馈，同时将共享增量里的所有 wish 标记完成。该结论缺少用途证据与逐 wish 判断。
