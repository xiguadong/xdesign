# 使用确认与验收的语法及阶段合规约束

规则集版本：0.1。日期：2026-10-12。状态：目标规范；规则、字段和检查结果要求不表示检查器或验收服务已经实现。

## 适用范围、依据与输入

适用于 `VModelAgents::VModelDevelopment::stakeholderValidation` 和 `WishToProduct::ContractedVModelDevelopment::stakeholderValidation`。关卡为 `Acceptance review`，允许的下一项工作标识为 `operationsHandover`。依据为[整体架构设计 0.2](../../../design/workflow_mbse_architecture.md)、[V-model 源模型](../../../v_model_agents.sysml)中的 `ValidationAgentBehavior`、`validationChecksNeeds` 及返工路径，以及[生命周期源模型](../../../wish_to_product.sysml)中的 `ValidationSpec`、`ValidationBundle`。

输入包括选定 wish 及其预期用途、利益相关方需求基线、已放行的系统验证包、受验产品配置、使用确认计划、完成契约、工作上下文、规则版本与关卡 AGENT 配置。项目初始化绑定工具发布 `T1`，其中 V-model、元模型、编译/解析、渲染与追溯机制全生命周期固定；本阶段只显式选择用户约束版本。系统验证评价并提供需求符合性的证据，已放行的包可能保留范围内例外；本阶段组织的是预期用途的确认材料。通用结构要求见[模型与追溯约束](../model_traceability/syntactic_constrains.md)和[运行约束](../workflow_execution/syntactic_constrains.md)。

## 允许工作与产出

允许在 `development` 制定或细化使用确认用例，执行已授权的使用场景，记录用户评价、场景结果、剩余问题及验收理由，建立与 wish、需求、产品版本和真实证据的引用，更新对应原生 view。产出为 `ValidationBundle`，其中包含实际 SysML 模型、支持材料、观察证据、追溯关系及检查记录。新判断与用户替代决定写入开发记录；从发布读取的输入保持只读。发现需求、设计或实现需要改变时，提交影响分析和返工候选。

支持材料采用 `validation_plan.md`、`validation_report.md`、`issue_disposition.md`、`completion_review.md`；同一材料拆分时用稳定范围标识追加文件名，如 `validation_report_<scope-id>.md`，拆分文件由包清单路由。项目采用其他命名时，应在本次选定阶段契约中给出唯一映射。模型和文档身份与版本依照[目录总说明](../README.md)，文件名不能单独充当版本证据。

## 规则

| ID | 约束判定 | 诊断位置或检查证据 |
| --- | --- | --- |
| AC-SYN-001 | 审查清单列明 wish、增量、尝试、产品配置、上游系统验证和利益相关方需求的身份与版本，并固定流程、规则、定义库及完成契约选择；缺少任一适用输入应报告缺项。 | 审查包清单、`WorkContext` 和上游引用字段。 |
| AC-SYN-002 | SysML 文本通过选定语言与库版本的解析、名称、类型及引用检查；确认用例、使用场景、验收关系和本模型 view 可以定位。自定义确认 dependency 必须声明工程含义，不能把 `verify` 或系统验证依赖改名当作使用确认。 | 模型文件、限定名、行列、语言检查输出与关系定义。 |
| AC-SYN-003 | `ValidationBundle` 具备非空的包身份、版本、基线、来源基线、wish、增量、迭代号和契约身份；`models`、`materials`、`evidence`、`traceLinks` 均有实际条目。当前源模型选择为 `ValidationSpec` 1.0；变更契约必须显式选择新版本。 | `ProducedBundle` 字段、包清单及 `expected` 选择。 |
| AC-SYN-004 | 材料按本阶段命名映射保存；计划列出场景、角色、环境、预期结果与评价方法，报告列出逐场景结果，问题处置列出未决项，完成评审按 wish 分列范围和结论。标题、材料身份、版本和所评产品基线必须齐全。 | 支持材料文件名、文档章节与包索引。 |
| AC-SYN-005 | 每项实际观察记录 `evidenceId`、`checkedBaselineId`、方法、实际结果、执行主体和时间，并链接可读取的日志、评价或场景记录及其选定版本。未执行、失败和结果不确定分别记录；计划文本、示例截图或默认布尔值不能填作实际通过证据。 | `Evidence` 条目、真实资源引用及原始输出。 |
| AC-SYN-006 | 每个纳入本次范围的 wish 都能定位到其预期用途、确认场景、受验产品与证据；共享材料引用同一稳定身份。完成记录按 wish 保存所选需求、设计、实现、验证与确认路径，不以增量级结果覆盖各 wish 的记录。 | wish 原生追溯模型、场景映射和完成选择清单。 |
| AC-SYN-007 | `checks.checkedBaselineId` 等于提交包基线；各检查字段引用真实检查或评审记录，保留适用、不适用、未执行与失败的区分。`contractChecked` 的源模型表达式被满足与 `Acceptance review` 获得有效决定分别记录。 | `BundleChecks`、规则执行清单、语义评审和决定记录。 |
| AC-SYN-008 | 决定记录包含判断者及 kind、授权范围、`Acceptance review`、所审 snapshot、结论、理由、时间和 `permittedNextWork = operationsHandover`；主体、授权与材料选择符合本 workflow 配置。人工接管条件按配置解释，不新增全局人工审批步骤。 | `ReviewDecision`、AGENT 配置和审查材料快照。 |
| AC-SYN-009 | 本阶段执行仅覆盖确认、验收材料和追溯更新；修改上游需求、设计、代码或受验配置须记录影响分析并建立受影响阶段的新尝试。产品与证据变更后，原决定保留并标明对新选择的适用性。 | 尝试输入输出、变更差异及 `impactAndRework` 记录。 |
| AC-SYN-010 | 用户改关卡结果生成关联旧决定的新决定，记录原因、例外规则、范围和允许工作；原失败事实、未执行检查及旧结果继续可读。后续调度单独检查实际材料可读、流程可解释和适配器可用，不借用户修改伪造这些前提。 | 用户修改历史、例外记录、有效决定选择与调度诊断。 |
| AC-SYN-011 | 本阶段工具选择与初始化 `T1` 绑定一致，包含固定工具及依赖；机器升级或用户规则修改不改 V-model、元模型和语言/渲染/追溯机制。新约束必须显式选版本，新检查保留其实际采用版本，旧检查不得重标。 | 工具锁定、约束选择、检查输入和工具依赖清单。 |
| AC-SYN-012 | 模型、view、确认材料和新决定保存到开发区，引用既有发布时固定只读内容。用户更改验收或完成决定、后续补证据均不回写旧发布；需发布变更时由跨阶段发布操作创建新对象，原发布的关系、决定和依赖保持不变。 | 保存目标、开发决定历史、发布引用及内容核对。 |

## 出口与返工

结构合规只允许形成可审查的材料选择。`Acceptance review` 的工程充分性由配置的人或 AI AGENT 根据[语义规则](semantic_constrains.md)判断。源模型的放行还要求有效当前决定、生产契约与当前来源基线满足，且 `systemReady` 有效；满足后进入 `operationsHandover`。待判断则等待，拒绝或有效停止条件则停止，材料失效或需要返工则按源模型进入 `impactAndRework`，选择最早受影响阶段并创建新尝试。

wish 完成由所选完成契约单独判定。若契约将移交纳入完成范围，应等移交证据与决定；若未纳入，应记录排除边界。阶段结束、工具成功和 V-model 运行结束不能替代完成决定。

## 示例

合格：一个 wish 的场景报告明确引用本次受验构建，使用者反馈与实际操作日志均能从包清单读取；确认用例、未决项及 AGENT 决定引用相同选择，完成记录注明还需移交后才能完成。复评采用显式新约束和固定 T1，记录写入开发区，原 R1 的验收决定不变。

不合格：将系统测试全部通过的摘要复制为验收报告，缺少使用者、使用场景和真实操作记录，却把 `semanticsPassed` 和 wish 完成同时置为真；随后以用户改结果为由覆盖 R1 包内决定。即使文件能解析，仍违反证据记录、逐 wish 完成和发布不可变要求。
