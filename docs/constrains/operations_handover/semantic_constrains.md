# 交付与运行移交的语义充分性约束

规则集版本：0.1。日期：2026-10-12。状态：目标规范；本文件规定评审依据，不声明已完成发布、投运、恢复或接收。

## 适用范围、依据与输入

适用于 `operationsHandover` 的 `Operations handover`。依据[整体架构设计 0.2](../../../design/workflow_mbse_architecture.md)、[V-model 移交职责](../../../v_model_agents.sysml)和[生命周期源模型](../../../wish_to_product.sysml)中的 `OperationsSpec`、`OperateAndObserve` 与 `WishToProductLifecycle`。输入是相同选定版本的验收结论、产品配置、发布清单、操作维护恢复材料、支持与生命周期计划、准备验证证据及未决项。

配置的人或 AI AGENT 判断这些材料是否足以支持本次交付及后续运行，说明理由和不确定性；文件齐全、工具成功和模板布尔值不能替代关卡判断。通用依据见[模型与追溯语义约束](../model_traceability/semantic_constrains.md)、[运行语义约束](../workflow_execution/semantic_constrains.md)与[目录总说明](../README.md)。

## 允许工作与产出

允许评价交付一致性、运行准备、接收能力、维护恢复方案和生命周期条件，形成有限定范围的开发移交决定及完成建议。允许要求补充演练、材料或返工，不能在评审中假定尚未发生的安装、接收、恢复、成功封存或支持承诺已成为事实。产出为带材料和证据引用的评审理由、未决项处置与新有效决定，写入开发区；结构见[本阶段语法约束](syntactic_constrains.md)。跨阶段[项目发布评审](../project_release/semantic_constrains.md)评价候选与最终发布，不移动本阶段关卡。

## 规则

| ID | 约束判定 | 诊断位置或评审证据 |
| --- | --- | --- |
| OPS-SEM-001 | AGENT 判断候选及实际成功封存的交付配置是否就是被验证、确认并审查的产品，差异是否有支持与处置；固定 T1 及依赖保持，用户约束采用显式版本。版本名相同而内容或依赖不同不能沿用结论，移交通过不能推定封存已成功。 | 工具/约束选择、候选与发布清单、差异及封存事实。 |
| OPS-SEM-002 | 安装、启动、运行环境、依赖和容量条件应足以支持选定使用范围；AGENT 解释准备验证与真实目标环境的差异及限制。只在开发机成功启动不能自然推导出接收环境已就绪。 | 环境模型、准备验证、差异说明及适用范围。 |
| OPS-SEM-003 | 接收方或承担接收职责的主体应有能力取得、理解并使用材料，责任边界与交接条件可执行；AI 或工具可以承担配置职责，但评审不能编造人员已阅读、培训或确认的事实。 | 移交记录、职责配置、演示/培训观察与未决接收项。 |
| OPS-SEM-004 | 操作说明覆盖正常流程、关键异常、限制和支持入口，并与交付版本的真实行为一致；AGENT 判断具备所需背景的操作者能否据此完成目标任务，发现缺步骤或不可执行命令须要求补充。 | 操作场景演练、指南对应配置和操作者反馈。 |
| OPS-SEM-005 | 恢复方案应覆盖本次系统关键故障，明确备份、恢复或回退条件、数据一致性与效果不确定时的核对方式；AGENT 依据演练及限制判断可恢复性，不能把计划存在当作恢复成功。 | 恢复计划、实际演练、数据核对与未覆盖故障。 |
| OPS-SEM-006 | 维护方案能持续识别、定位并处理已知失效和变更需求，版本兼容、依赖更新、配置维护及支持责任有可执行安排；AGENT 评估对已验收行为和既有证据的影响，而非仅查看指南标题。 | 维护场景、支持能力、依赖策略及变更影响说明。 |
| OPS-SEM-007 | 运行观察应足以发现偏离 wish 目标、需求边界或验收条件的问题；事件、反馈和维护结果应能追溯到实际产品版本，并触发影响分析及相应阶段的新尝试，不能只在运行记录中关闭工程问题。 | 观察计划、事件模板、问题到阶段的映射和再评审条件。 |
| OPS-SEM-008 | 生命周期计划应说明继续运行、演进、暂停和退役的条件、责任与下一项工作；AGENT 判断这些条件能否由真实观察支持。移交通过不能预先批准以后任意增量或任何退役操作。 | 生命周期接口、触发条件、授权范围及后续评审职责。 |
| OPS-SEM-009 | AGENT 按 wish 的完成契约判断交付、接收、投运和后续运行哪些属于完成边界，并逐 wish 说明尚缺内容；V-model 结束或 `operationsReady` 只提供流程事实，不替代完成决定。 | 完成契约、逐 wish 完成路径、接收证据及决定理由。 |
| OPS-SEM-010 | 对剩余风险或用户修改后的例外，判断其范围、约束、责任及下游影响是否明确，保留真实失败和未执行事实。允许推进的决定只覆盖所声明工作，不能使缺失交付物、不可读取输入或不可用执行适配器成为已满足前提。 | 未决项、用户新决定、例外范围、原始检查与调度前提。 |
| OPS-SEM-011 | AGENT 判断候选是否已固定为可独立审查的内容，最终发布决定是否指向该候选，封存前核对是否仍匹配；候选身份不依赖尚未产生的最终决定。核对或封存失败应保持失败事实，不能凭通过关卡宣布成功发布或交付。 | 候选身份、发布决定、核对选择、封存结果和交付声明。 |
| OPS-SEM-012 | 发布保留的原生模型/view、约束确定内容、原生关系、证据及各自历史输入依赖应足以解释成果，遗漏须补齐，无关历史不强制复制；早期检查保留原范围，不重标为针对最终内容执行。新开发判断、外部撤回说明及重渲染缓存不能改写原 release；损坏不能作为同次发布的新版本接受。 | 依赖充分性、证据原范围、发布只读核对和外部说明。 |

## 出口与返工

通过理由应说明本次产品可向哪个接收范围交付、哪些条件适用、为何运行维护材料充分。有效当前决定及源模型其他放行条件共同确定 `operationsReady`；关卡中的下一项工作仍是 `lifecycleManagement`，外层生命周期在开发放行后进入 `operate`。实际发布交付还须记录跨阶段发布操作的成功封存；候选包或关卡通过均不能替代该事实。不确定或未完成接收事项按范围保持待判断、补充材料或返工；拒绝及有效停止条件按所选流程处理。

运行观察揭示原验收主张不再成立、配置不一致或恢复方案不足时，建立影响分析，保留旧版本事实并回到最早受影响阶段的新尝试；演进走新增量，不在原移交决定上无限扩展范围。用户可改关卡结果，明确例外后的有效决定与实际调度前提分别评价。

## 示例

合格：AGENT 根据交付配置、接收环境演练和恢复观察接受限定范围的移交，说明支持责任、运行观察入口与尚需复核的限制，并按各 wish 的完成契约分别作出完成建议。

不合格：发布文件齐全便宣布运行已准备好，未核对接收环境、恢复可行性和支持责任；随后运行事故被当作单次维护记录关闭，未评价其对设计与验收决定的影响。
