# 利益相关方需求：语义充分性约束

规则集版本：0.1。日期：2026-10-12。状态：依据当前架构新增的目标约束，不表示现有关卡或检查器已经实现。

## 适用范围、依据与输入

适用于 `stakeholderNeeds` 的 Needs review，由该 workflow 配置的人或 AI AGENT 判断 Wish 理解、使用场景与验收意图是否足以开始系统需求工作。AGENT 的主体种类不改变评审问题和证据要求。

依据为 [整体架构 0.2](../../../design/workflow_mbse_architecture.md) 的“生命周期中的内容分类”“用户约束如何演进”“开发与发布”“一次发布的执行过程”，[V-model](../../../v_model_agents.sysml) 的 Needs review，以及 [产物模型](../../../wish_to_product.sysml) 的 `NeedsSpec`。通用约定见 [总说明](../README.md)、[模型与追溯语义约束](../model_traceability/semantic_constrains.md) 和 [项目发布语义约束](../project_release/semantic_constrains.md)。

评审输入为按 [syntactic_constrains.md](syntactic_constrains.md) 组织的固定审查包，包括项目初始化绑定的工具发布、显式采用的用户约束版本、原始 Wish、建模解释、利益相关方/场景、验收意图、约束/假设、开放问题、结构检查及来源材料；继承已有成果时包含只读发布选择。工具诊断提供事实；AGENT 必须对以下工程问题记录判断、理由、证据、缺口与不确定性。规则可以演进，固定 V-model、公共元模型及编译/渲染/追溯机制不能在阶段评审中任意切换。

## 允许工作与产出

允许在开发区解释与澄清预期用途、识别使用角色、比较冲突诉求、调整场景和验收意图、确认范围并提出返工；判断和用户替代决定同样写入开发记录。交付的是足以约束后续需求的使用意图及其审查决定。本阶段制定使用确认/验收意图，后续系统需求阶段制定系统验证计划；本阶段不要求未来产品已完成实际验收。已有发布不被本次澄清或结果修改回写，新成果通过后续新发布交付。

## 规则表

| ID | 约束与判定 | 评审证据 |
| --- | --- | --- |
| NEED-SEM-001 | 建模意图忠实表达原始 Wish 的目标、动机和限制。解释性补充能追溯到澄清或明确假设，不能把 AGENT 的偏好当成用户要求，不能删除不利于实现的原始诉求。 | 原始提交与解释对照、澄清记录、假设及其责任主体。 |
| NEED-SEM-002 | 利益相关方与使用角色覆盖本范围中会使用、维护、支持或受结果影响的主体；不同角色的目标与约束足以区分。没有必要枚举无关角色，对遗漏角色应解释为何不影响本增量。 | 角色清单、使用环境、影响分析与范围说明。 |
| NEED-SEM-003 | 预期用途和范围明确到可以判断“何时、由谁、为何使用，获得何种结果”。增量内外边界及与既有发布的关系清楚，继承成果与本次修改能区分。项目自身 MBSE 自举的用途与业务 Wish 的用途分别说明；对本产品应涵盖固定工具、可变约束及开发/发布隔离的使用场景。 | 用途描述、增量边界、继承发布、项目上下文及读写场景。 |
| NEED-SEM-004 | 场景能展示目标达成的真实交互，包括本范围关键的前置条件、外部依赖、异常及恢复情形。AGENT 根据风险与使用环境判断覆盖是否充分，场景条目数量不能替代该判断。 | 正常/异常场景、关键路径、依赖与风险映射。 |
| NEED-SEM-005 | 验收意图描述可观察的用户结果，并说明拟采用何种使用确认方式、环境和责任主体。应能在后续 Acceptance review 判断用途是否实现；不能只写“模型可解析”“所有工具成功”或“流程结束”。 | 验收意图与场景对应、观察方式、验收责任和边界。 |
| NEED-SEM-006 | 系统限制、业务限制、使用环境、必要质量属性及数据/接口前提已识别，其来源与强度清楚。未经确认的假设标明验证责任和影响，不能静默作为已确认约束。 | 约束来源、质量诉求、假设清单、拟解决方式。 |
| NEED-SEM-007 | 相互冲突的利益相关方诉求、Wish 之间的共享约束和优先级已经显式处理。已决取舍有授权依据；未决冲突不会使下一阶段无法解释目标，若仍有影响须作为阻断或受限范围记录。 | 冲突清单、取舍理由、授权范围、共享项目引用。 |
| NEED-SEM-008 | 开放问题与不确定性披露充分，区分本阶段必须解决的问题和可带入系统需求的待办；后者有责任、处理条件及对推进范围的影响。不得因表格填写完整而省略关键未知。 | 开放问题、风险、责任与处理条件、放行范围。 |
| NEED-SEM-009 | 当前意图可以被细化为系统需求，足以区分行为要求、质量要求和外部约束；不会无依据地把某实现方案固化为用户需要。确为用户指定的技术约束保留其来源和理由。 | 意图到需求候选的映射、方案假设、明确技术限制。 |
| NEED-SEM-010 | 证据强度支持所宣称的“理解/确认”程度。缺少利益相关方直接确认时，AI 推断、文档分析或代理确认的来源及局限披露，由 AGENT 判断是否足以推进；不能编造访谈或接受记录。早期确认保留原意图、规则和材料选择；复用须判断适用性，不能重标为对最终发布内容进行过确认。 | 原始来源/确认记录、原规则与材料、选择差异及复用理由。 |
| NEED-SEM-011 | Needs review 的理由、剩余问题和允许工作与上述评估一致，只对选定版本与范围有效。用户例外形成新的有效开发决定，其风险与原失败事实可查；材料或显式采用的约束变化后重评，用户规则或主体分配不移动固定关卡。 | 开发判断、约束版本、审查包、例外与影响分析；[工作流执行语义约束](../workflow_execution/semantic_constrains.md)。 |
| NEED-SEM-012 | AGENT 判断澄清、规则变更、追溯更新和决定修改的范围遵守开发/发布边界，继承发布的原意图、证据与决定继续保留原含义。若新解释影响已交付主张，应记录影响并为新成果评审，不能用改变旧发布来消除差异或把候选工具机制自动替换项目绑定。 | 继承发布、开发差异、原证据/决定与新审查选择；[项目发布语义约束](../project_release/semantic_constrains.md)。 |

## 出口与返工

AGENT 输出待判断、通过、需要返工或拒绝，并引用本次审查包。通过意味着 Wish 理解、场景和验收意图在获准范围内足以进入 `systemRequirements`，不表示后续产品已满足 Wish。结构通过和工具成功均不单独产生此结论。

关键用途不清、不可接受的诉求冲突或无从判断验收意图时，在开发区返回本阶段澄清；来源、上游范围或显式选定的用户约束变化时，按项目固定流程先评估影响。局部问题允许受限推进时，由有效决定明确范围、理由和待办。用户修改结果形成新的开发决定，保留原判断、检查事实和已有发布；后续工作依据新决定开展，后续发布保存新成果，不更新原发布。

## 合格与不合格例子

- 合格：Wish 要求“暂停后能继续原工作”。场景涵盖等待 AGENT 时暂停、重启后恢复原审查材料和既有决定，验收意图要求使用者能确认恢复位置与未重复执行的工作；未确认的外部执行效果作为开放问题交给后续需求处理，Needs review 记录其影响及放行范围。
- 不合格：把同一 Wish 解释为“显示一个暂停按钮”，以“页面存在且可点击”作为全部验收标准，没有恢复位置、已发生效果或使用结果。即使模型和字段完整，意图仍不足以表达原诉求。
- 允许披露后判断：尚未完成用户访谈，但原始提交和澄清消息能支持明确用途。AGENT 引用这些真实来源，说明未获直接确认的部分及不确定性；是否放行取决于其工程判断，不得伪造“用户已验收”。
