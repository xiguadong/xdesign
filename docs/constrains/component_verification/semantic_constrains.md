# 组件验证阶段的语义约束

规则集版本：0.1。日期：2026-10-12。状态：目标约束。

适用架构：[整体架构 0.2](../../../design/workflow_mbse_architecture.md)。项目初始化绑定工具发布 `T1` 及固定依赖：V-model、公共元模型、编译/解析、渲染和追溯机制在项目生命周期内保持不变，工具升级另行迁移。用户语法/阶段约束 SysML、语义评审约束 SysML、文档规范及外部规则可以发布新版本，新尝试显式采用；既有证据和决定保留原选择。

## 适用范围及依据

本规则用于判断实际组件证据是否充分支持“该组件符合选定详细设计”的工程主张，对应 `Component review`，后续工作为集成与接口验证。判断由该 workflow 配置的人或 AI AGENT 作出，记录理由、依据、不确定性和适用范围；这里不设置全局人工审批，也不宣称检查器已经实现这些规则。工具结果、结构检查通过和关卡通过分别保留各自含义。

依据：[整体架构设计](../../../design/workflow_mbse_architecture.md)（0.2）的“用户约束如何演进”“一次发布的执行过程”“最小可执行范围”，[V-model 定义](../../../v_model_agents.sysml)的 `ComponentVerificationAgentBehavior` 与 `componentVerifiesDesign`，以及 [Wish 生命周期模型](../../../wish_to_product.sysml)的 `ComponentVerificationSpec`、`Evidence` 和 `ContractedVModelDevelopment::componentVerification`。

通用要求见[路由说明](../README.md)、[模型与追溯语义约束](../model_traceability/semantic_constrains.md)、[工作流执行语义约束](../workflow_execution/semantic_constrains.md)；机械结构要求见[本阶段语法约束](syntactic_constrains.md)。

## 输入、允许工作与产出

评审和用户替代决定形成新的开发记录；不回写旧发布。纳入后续发布的早期证据保留其真正检查输入、上游模型、实现和规则版本，AGENT 评价它对当前选择的适用性，不能重标为针对最终内容重新执行。相关要求见[项目发布语义约束](../project_release/semantic_constrains.md)。

评审输入是同一版本选择下的组件构建、详细设计及其约束、验证用例/程序、实际观测与原始证据、环境配置、覆盖及缺口、异常处置、检查结果和变更影响。以 Build review 的当前材料为顺序输入，以详细设计为符合性依据。

允许评价测试方法、复核观察、识别设计或实现问题、要求补充实验、提出缺口和返工建议。产出是逐项语义评价及 `Component review` 决定，说明支持了哪些设计主张、仍存哪些缺口、能否在所选范围进入集成；不能用评审文字代替未发生的组件验证。

## 规则表

| ID | 约束判定 | 评审证据 |
| --- | --- | --- |
| CV-SEM-001 | 验证对象应是本次选定的实际组件构建，设计目标与该 wish/增量相关。历史构建、原型或替代件的证据只有在差异及适用性获得明确论证时才可支持当前对象。 | 构建清单、设计基线、wish 追溯、版本差异及适用性说明。 |
| CV-SEM-002 | 证据必须来自实际执行、检查、分析或演示，且观测与结论可复核。测试计划、用例数量、模型解析成功或 `verify`/dependency 关系存在本身不足以证明组件符合性。 | 原始日志、执行记录、分析输入及方法、可复算结果。 |
| CV-SEM-003 | 用例和方法能够检验详细设计要求的结构、行为、接口及约束；评价准则来自被选定的设计，不因已观察结果而降低。以实现自身输出作为唯一预期值时，应有独立依据避免自证。 | 用例设计、目标约束、预期结果来源、程序与设计映射。 |
| CV-SEM-004 | 覆盖应包括当前范围内正常、边界、错误输入、异常路径及恢复行为；按风险解释哪些设计目标尚未验证。行覆盖率或“全部已写用例通过”不能代替设计目标覆盖。 | 设计目标覆盖、边界/故障用例、风险清单、未覆盖项理由。 |
| CV-SEM-005 | 环境、替代件、依赖配置和测量方法足以代表设计的适用条件。工具误差、模拟偏差、时序与资源限制会影响结论时应纳入评估，不得把受限实验的结论扩大到所有环境。 | 环境对照、测量校准/精度、替代件差异、资源与时序记录。 |
| CV-SEM-006 | 通过结论必须由实际观察支持设计的判据；结果未知、中断、缺少日志或无法解释的波动属于不确定性，不能作为通过证据。不适用项的排除应符合当前设计范围。 | 逐项判据与观察、未知项核对结果、波动分析、排除理由。 |
| CV-SEM-007 | 失败及异常的原因、影响和处置应可信。重跑通过需要解释失败如何消除，修复后验证相关目标及回归影响；仅删除失败、重复执行直到偶然通过或改低阈值不构成问题闭环。 | 原始失败、根因分析、修订内容、复验/回归结果、处置结论。 |
| CV-SEM-008 | 组件边界内的接口假设应与架构和详细设计一致；使用 mock/桩的结果应说明哪些交互尚待集成验证。组件通过不能推导出真实组件间协议、性能及故障传播已经验证。 | 接口假设、桩行为、接口版本、移交集成的限制与待验证项。 |
| CV-SEM-009 | 变更影响评价应识别相关设计、实现、依赖、程序或环境变化导致的证据失效范围，确定必要复验及更早返工位置；复用证据保留原输入/规则并论证仍能支持当前设计主张，不把历史执行重标为最终版本。共享组件服务多条 wish 时，复用证据需分别说明范围。 | 依赖追溯、变更差异、受影响目标/证据清单、复验与复用理由。 |
| CV-SEM-010 | 未解决缺口与残余风险应允许后续集成做出可靠判断；阻塞性设计不符合不得被“检查成功”掩盖。若有效决定允许范围内例外，应说明授权、限制、依据及后续处置，原失败仍是失败。 | 问题分级、残余风险、例外范围、后续集成前提、当前有效决定。 |
| CV-SEM-011 | `Component review` 的理由应与所选审查包一致，明确支持的组件/设计范围和是否允许 `integrationVerification`。AGENT 或用户修改决定形成新的开发记录，不能修改旧发布，不能把缺失证据变成已执行事实，也不能据此宣称系统需求、预期用途或 wish 已全部满足。 | 语义评价、决定理由、证据引用、允许后续工作、替代决定历史。 |
| CV-SEM-012 | 对承担工具绑定、保存、封存或读取的组件，实际证据应按详细设计支持 T1 及依赖不被日常编辑替换、开发保存不覆盖发布、候选内容不跟随后续编辑、失败封存不冒充成功、发布内容可由原工具读取。证据明确对上层 R1/R2 隔离场景支持的职责与局限，不能由组件通过推定全系统发布隔离已经成立。 | 组件故障/边界运行、内容摘要与写入目标、候选/封存状态、原 T1 读取结果。 |

## 出口与返工

AGENT 依据同一审查包记录待判断、通过、返工或拒绝等结论。只有当前范围的有效关卡决定以及流程规定的执行前提成立，协调器才允许进入集成；语法与语义评价的通过标记不能单独替代决定。

验证方法或证据不足时补充组件验证；实现错误返回实现；设计目标或接口假设错误按变更影响返回详细设计或更早阶段。返工保留失败及原决定，用新尝试形成修订证据。用户修改决定时记录新的有效范围和限制，真实观察继续保留。

## 例子

合格：告警组件按详细设计要求验证阈值上下边界、无效传感值和冷却恢复。一次恢复失败保留日志并定位为计时状态错误；修复后复验和回归均满足选定判据。AGENT 说明桩通信不支持真实网络接口的结论，将该项移交集成验证后，在当前组件范围作出允许集成的决定。

不合格：组件只在正常输入下运行一次，用“测试 100% 通过”证明全部详细设计符合；未执行断线恢复测试，且计时超时日志缺失仍标成功。即使模型与结果表结构合法，也违反 CV-SEM-002、004、006，须补充证据或返工。
