# 系统需求：语义充分性约束

规则集版本：0.1。日期：2026-10-12。状态：依据当前架构新增的目标约束，不表示现有关卡或检查器已经实现。

## 适用范围、依据与输入

适用于 `systemRequirements` 的 SRR，评判系统需求与系统验证计划是否足以表达所选 Wish 的意图并指导系统架构与方案工作。由该 workflow 配置的人或 AI AGENT 对固定审查材料作出判断，工具提供的解析、覆盖和差异事实不能替代关卡结论。

依据为 [整体架构 0.2](../../../design/workflow_mbse_architecture.md) 的“生命周期中的内容分类”“用户约束如何演进”“开发与发布”“一次发布的执行过程”，[V-model](../../../v_model_agents.sysml) 的 Requirements 阶段与 SRR，[产物模型](../../../wish_to_product.sysml) 的 `RequirementsSpec`。通用约定见 [总说明](../README.md)、[模型与追溯语义约束](../model_traceability/semantic_constrains.md) 和 [项目发布语义约束](../project_release/semantic_constrains.md)。

输入为按 [syntactic_constrains.md](syntactic_constrains.md) 固定的审查包：项目初始化绑定的工具发布、本次显式采用的用户约束版本、Wish 与 Needs 基线、有效 Needs review 决定、需求模型和规格、约束、系统验证计划、追溯矩阵、真实检查及开放问题；继承已有成果时包含只读发布选择。评审记录逐条说明判断、理由、证据、缺口与不确定性；用户规则可演进，固定 V-model、公共元模型及编译/渲染/追溯机制不在本阶段任意切换。

## 允许工作与产出

允许在开发区细化、合并或拆分需求，消除歧义/冲突，制定验证判据和计划，评估可行性并提出上游澄清；判断和用户修改形成开发记录。系统需求表达系统必须实现的行为与属性，为架构选择提供边界；来源明确的技术约束可以保留。系统验证计划和上游使用确认/验收意图分别支持需求符合性与预期用途判断。已有发布的需求、计划和决定只读继承，变更成果经新候选及新发布交付。

## 出口与返工

SRR 的正常通过表示所选需求及系统验证计划在批准范围内足以进入 `systemArchitecture`，不代表需求已由实际系统满足。AGENT 应记录待判断、通过、需要返工或拒绝，以及支持结论的理由与材料。

需求歧义、缺失关键行为或方法不能验证要求时，在开发区返回系统需求阶段；无法从上游确定要求时，按固定流程回到利益相关方需求阶段。受限推进或用户例外明确范围、未满足项与责任，形成新的开发决定，不能改变既有事实或已发布内容。相关材料或显式采用的用户约束变化后重新组织选择和判断，历史保留原范围；变更成果进入后续新发布，工具升级另行设计迁移。

## 合格与不合格例子

- 合格：需求规定“恢复时使用暂停前已固定的审查材料版本；已提交决定不得因重复恢复生成第二条事实记录”。系统验证计划分别安排材料版本核对与重复恢复场景，说明受控基线、观察字段和判据；SRR 评估外部效果不确定的处理约束后给出是否足以进入架构的结论。
- 不合格：需求仅为“支持恢复”，计划为“启动成功即可”。它没有说明恢复状态、材料、重复效果或判据，不能支持原 Wish 的工程目标，模型可解析也应返工。
- 需分别判断：代码覆盖率工具将来可能覆盖大部分代码，但本阶段只能评审相关计划是否适合指定需求；覆盖率不能替代版本一致性、恢复语义或使用验收的证据。
