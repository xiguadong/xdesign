# 系统需求：语法与阶段合规约束

规则集版本：0.1。日期：2026-10-12。状态：依据当前架构新增的目标约束，检查器实现状态不由本文声明。

## 适用范围、依据与输入

适用于初始 V-model 的 `systemRequirements` 阶段、`RequirementsBundle` 和 SRR 审查材料。语法层覆盖 SysML 解析和类型/引用合法性、结构化需求与文档、阶段关系及实际记录存在性；工程充分性见 [semantic_constrains.md](semantic_constrains.md)。通用约定见 [总说明](../README.md)。

依据为 [整体架构 0.2](../../../design/workflow_mbse_architecture.md) 的“生命周期中的内容分类”“开发区的三类模型”“用户约束如何演进”“两个区域的操作边界”，[V-model](../../../v_model_agents.sysml) 的 `RequirementsAgentBehavior`、`systemRequirements`，以及 [产物模型](../../../wish_to_product.sysml) 的 `RequirementsSpec`、`RequirementsBundle`。现有 `RequirementsSpec` 的契约版本 1.0 与本文规则集版本分别记录；工具机制按项目初始化绑定全程固定，阶段用户约束可以显式选择新版本。

输入为选定 Wish/增量与工作上下文、利益相关方需求基线、同一范围上当前有效的 Needs review 决定、项目上下文及已确认/待处理限制、项目初始化绑定的工具发布及固定依赖、本次显式采用的用户约束版本及本阶段执行者和 SRR AGENT。采用 `ContractedVModelDevelopment` 时，本阶段上游为 `stakeholderNeeds.produced`；必须保留实际使用的版本。已有发布作为输入时保存只读继承的发布及内容选择。

## 允许工作与产出

允许在开发区细化系统需求、整理功能/质量/接口/运行约束、建立来源与细化关系、制定系统验证计划、记录冲突与开放问题，并更新 Wish 模型和原生 view。用户规则 SysML、语义标准及文档规范修订形成新版本，显式选择后参与新的尝试；它们不改写固定工具机制。实现方案可作论证材料或候选假设，不能声称系统架构阶段已完成。已有发布仅作为只读输入，修改成果由后续新发布承载，见 [项目发布语法约束](../project_release/syntactic_constrains.md)。

必须提交需求模型及实际支持文档：需求规格、约束、系统验证计划、追溯矩阵、开放问题及版本清单。建议文档名为 `requirements.md`、`constraints.md`、`system_verification_plan.md`、`traceability.md`、`open_questions.md`；阶段契约登记实际位置与归属，合并文档时登记各部分稳定章节。使用确认/验收意图引用上游材料，系统验证计划说明如何判断系统需求满足。

## 出口与返工

结构结果合格允许把本次材料提交 SRR，不能单独放行。SRR 由配置的 AGENT 对同一材料选择作语义判断，再依据当前有效开发决定与项目固定流程的运行前提进入系统架构与方案阶段。显式采用新用户规则不改变该出口或工具绑定。

结构错误或缺失计划在开发区返回系统需求阶段修正；上游用途、场景或验收意图不足时，按固定流程的影响评估回到利益相关方需求阶段。上游决定、材料或显式采用的用户约束变化时，保留历史并重建受影响选择。用户范围内例外形成新的有效开发决定，原工具失败、未执行事实和已发布内容不变。工具绑定不一致先修复配置，升级属于单独迁移设计，不能在普通返工中换用工具。

## 合格与不合格例子

- 合格：`REQ-017` 原生需求引用 `W001/SCN-01` 的选定版本，`SVP-017` 计划项通过适用的 verify 关系关联该需求，包含恢复环境、操作步骤、判据与拟保留证据；计划标注未执行，实际结构检查与 SRR 决定分别保存。
- 不合格：文档表中列出 `REQ-017`，模型无对应身份，验证计划只写“运行测试”，却以一条 verify 关系宣称系统已验证。分别违反身份、计划结构和实际记录约束。
- 结构合格但仍待语义判断：需求正文、来源和验证字段都存在，但性能判据写成“较快”。字段齐全不说明判据可测量，SRR 应按语义规则判断是否需要返工。
- 不合格：用户修改需求规则后将 SRR 移到实现之后，或把新需求和替代决定直接覆盖 `R1`。用户规则可演进，但固定 gate 与已有发布的内容均不随之变化。
