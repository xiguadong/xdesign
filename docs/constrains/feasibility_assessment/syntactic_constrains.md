# 可行性评估：语法校验规则

规则集版本：0.1。状态：目标约束草案。日期：2026-10-12。

适用架构：[整体架构 0.2](../../../design/workflow_mbse_architecture.md)。项目初始化绑定工具发布 `T1` 及固定依赖：V-model、公共元模型、编译/解析、渲染和追溯机制在项目生命周期内保持不变，工具升级另行迁移。用户语法/阶段约束 SysML、语义评审约束 SysML、文档规范及外部规则可以发布新版本，新尝试显式采用；既有证据和决定保留原选择。

## 适用范围、输入与产出

对应 `AssessFeasibility`、`FeasibilitySpec/FeasibilityBundle` 和 `Feasibility review`，依据[生命周期模型](../../../wish_to_product.sysml)及[整体架构 0.2](../../../design/workflow_mbse_architecture.md)。遵循[公共规范](../README.md)、[模型](../model_traceability/syntactic_constrains.md)与[运行](../workflow_execution/syntactic_constrains.md)规则，本文不代表评估已实际执行。

输入为已澄清 Wish、工作上下文、项目初始化绑定 T1 及固定依赖、固定输入基线和所选用户约束版本。允许建立概念候选、评估限制/成本/风险、核实工具能力、生产评估材料及追溯/view；不提前生产需求批准或产品完成事实。输出为概念与假设原生模型、可行性依据、成本/风险、继续建议、实际检查与审查包，写入开发区持久资产/记录。继承旧发布只读，不把评估结果或用户新决定回写旧发布。

## 规则

| ID | 约束与判定方法 | 诊断位置 |
| --- | --- | --- |
| FEAS-SYN-001 | 输入 Wish、增量、迭代、澄清选择与上下文输入基线明确，可恢复实际内容；评估产物的来源基线与上下文匹配。 | 输入清单、上下文与产物 |
| FEAS-SYN-002 | 实际材料覆盖候选概念、初始约束、可行性假设、研究依据、成本/风险和继续建议，按公共规范命名及标注版本；合并章节可定位。 | 文件、章节、产物清单 |
| FEAS-SYN-003 | 实际概念模型可解析，有候选/约束/假设及 Wish 引用，维护原生 view；定义一个 `FeasibilityBundle` 不能替代内容。 | 原生模型、工具诊断、view |
| FEAS-SYN-004 | 候选有身份、适用范围和比较维度，选取/排除依据可定位；单候选明确记录不适用其他方向的原因。 | 候选及比较清单 |
| FEAS-SYN-005 | 假设、成本、风险和工具能力主张关联来源、选定版本与待核实状态；试验/调研日志注明实际执行输入、方法、主体、时间和观察，保留失败及未知；复用旧调研/检查保留真正输入/规则与支持范围并附适用性判断，不重标为当前内容执行。 | 假设表、依据及实际观察 |
| FEAS-SYN-006 | 评估模型、资料、证据和 Wish 建立合法的类型化追溯，外部资料有版本及章节定位；共享材料引用同一身份。 | 关系、外部引用及端点 |
| FEAS-SYN-007 | 产物契约身份/版本、实际包身份/版本、源与目标基线、Wish/增量/迭代一致，必需模型、资料、证据和关系齐备；包状态由实际检查支持。 | `FeasibilitySpec` 与包清单 |
| FEAS-SYN-008 | 可行性结论、结构结果与 `Feasibility review` 决定分开，布尔值 `feasible` 或 `contractChecked` 不代替检查与判断记录。 | 检查、结论和决定 |
| FEAS-SYN-009 | 审查包固定材料、规则、诊断、风险与问题；决定主体/授权匹配本 workflow，关卡为 `Feasibility review`，下一工作为 `development`。 | 审查包与当前决定 |
| FEAS-SYN-010 | `proceedAuthorized` 有当前可行性判断、契约检查及有效决定支持；不足进入 `holdForAuthority`，补材料或范围变更形成新选择和尝试。 | 出口、状态、适用性记录 |
| FEAS-SYN-011 | 可行性审查列出固定工具机制与可变用户约束：T1 及依赖匹配初始化绑定，试验不自动替换内核；用户语法/语义约束 SysML、文档规则/外部规范有版本选择，修订规则由新尝试显式采用。 | 工具绑定核对、约束版本与试验/尝试清单。 |
| FEAS-SYN-012 | 对本产品核心范围，概念/风险材料包含开发写入、候选内容固定、只创建新发布、旧发布只读、失败封存状态及原 T1 读取的接入方案，列出 R1 修改后再 R2 的后续验证方向。方案或试验状态与真实能力分开，材料更新只产生新开发选择。 | 核心目标—概念—风险映射、接入方案、后续验证准备。 |

## 出口与返工

与[语义评审](semantic_constrains.md)共同支撑当前可行性关卡。通常只有可行性及有效决定支持才进入嵌套开发流程的利益相关方需求阶段；不足按外层流程等待处理。用户例外按公共协议新增开发决定留存，不补造无法取得的依赖、材料或证据。发布另按[项目发布语法规则](../project_release/syntactic_constrains.md)执行，不改变现有 V-model 阶段。

## 判定示例

合格结构：能力试验固定 Pilot 和库版本、实际解析/view 输出及局限，成本风险与继续建议引用这些观察，决定明确准许 `development`。

不合格结构：引用一个工具首页就填“已支持完整关卡执行”；或没有真实检查，仅通过模型的 `feasible=true` 进入开发。
