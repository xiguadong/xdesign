# Checkpoint library

Project-level, Git-tracked authoring source for reusable checkpoints. A checkpoint is a
named verification recipe that a flow can bind at wish creation:

- **syntactic** — a fixed rule set with an executor (a project checker script or an agent
  CLI + model) and the project files the rules read. The executor answers the declared
  rules; assessments record script or agent authority accordingly.
- **semantic** — criteria and permitted judges (agent/human) for a semantic gate.

The operational run store (`.xdesign/`) stays separate: a wish freezes the library
definition it bound at `init`, so later edits here never change an existing run.

## Layout

```
checkpoints/
  README.md                     this file
  library.json                  user-maintained entries (created by `xdesign checkpoint save`)
  scripts/<checkpoint_id>.py    scripts generated by the scaffold action
```

`library.json` is created on the first save; a missing file means the binary's built-in
entries only. Built-in seeds expose the four SimpleFlow syntactic checkers and the
SimpleFlow semantic gate; they are read-only catalog entries.

## Add or update a checkpoint

Through the operator page (`xdesign web` → Checkpoints) or the CLI:

```sh
xdesign checkpoint list
xdesign checkpoint show requirements-rationale-and-trace
xdesign checkpoint save --request cache/new-checkpoint.json
```

A save request is one JSON object. Syntactic example:

```json
{
  "checkpoint_id": "docs-links-resolve",
  "title": "Relative documentation links resolve",
  "description": "Every relative Markdown link in the design pages resolves to an existing file.",
  "kind": "syntactic",
  "tags": ["docs"],
  "rules": [
    {"rule_id": "links-resolve", "condition": "Every relative link resolves.", "reads": ["docs/"]}
  ],
  "inputs": ["docs/design/flow.md"],
  "executor": {"mode": "script", "command_uri": "checkpoints/scripts/docs_links_resolve.py"},
  "create_script": "scaffold"
}
```

`create_script: "scaffold"` writes a deterministic checker scaffold at
`checkpoints/scripts/<checkpoint_id>.py` (the URI must match). The scaffold implements the
runtime checker protocol (`--list-inputs`, raw report with `input_sha256`) and answers
every declared rule as failed with `rule not implemented: <rule_id>` until the author
edits the rule functions. A script that already exists is reused by setting
`"executor": {"mode": "script", "command_uri": "<path>"}` without `create_script`.

**Script identity.** The shipped `tools/checks/*.py` scripts reject an invocation whose
`--checker-id` differs from their hardcoded id. When reusing one, set the optional
syntactic entry field `"checker_id"` to that identity (for example
`"simpleRequirementsCheck"`); the frozen plan then uses it as the assessment assessor while
`checkpoint.library` keeps the library provenance. Generated scaffolds echo whatever
`--checker-id` the runtime passes, so they need no `checker_id`.

A syntactic entry with an agent CLI executor omits `command_uri` and uses
`"executor": {"mode": "cli", "cli": "codex", "model": "gpt-6-astra"}`; no scaffold is
generated for CLI entries.

Semantic example:

```json
{
  "checkpoint_id": "verification-evidence-complete",
  "title": "Verification evidence answers every requirement",
  "description": "A permitted judge can re-examine the retained evidence and see each requirement answered.",
  "kind": "semantic",
  "tags": ["verification"],
  "criteria": [
    "Every requirement has retained evidence a reader can re-examine.",
    "The evidence and the record stand on their own without re-asking the author."
  ],
  "judges": {"agent": true, "human": true}
}
```

## Bind it to a wish

```json
{"schema_version": 1, "checks": [
  {"checkpoint_id": "simpleRequirementsAccepted", "mode": "library",
   "library_id": "requirements-rationale-and-trace"},
  {"checkpoint_id": "simpleDesignAccepted", "mode": "default"}
]}
```

```sh
xdesign init WISH_ID --flow simple-flow --checks cache/checks.json
```

Library bindings are accepted for the four syntactic SimpleFlow gates and the SimpleFlow
semantic gate `verificationAccepted`. The frozen plan records the library id together with
the rules, executor, and work inputs, so `next`/`check` never read `library.json` at run
time. See `web/SPEC.md` section 9 and the operator design page for the full contract.

## Verification

A checkpoint edit is verified by listing/showing it, binding it at `init`, and running
`next`/`check` against a wish; the initial-save validation covers ids, kinds, rule/input
shape, existing scripts, executor shape, and history bookkeeping.
