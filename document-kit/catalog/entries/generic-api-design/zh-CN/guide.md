# API 设计编写指南

本条目用于为一个 API 建立精确且可追踪的设计契约。作者应说明 API 在指定层次中的职责、声明和调用语义，并用不变量和错误行为限定实现空间。API 页不是执行记录，也不应把多个不相关操作合并为缺乏所有权的清单。

## 问题、边界与论证方法

设计论证应先确定 API 类型和边界，再给出语言级声明、输入输出所有权、错误和副作用。行为章需要说明合法调用顺序和并发或资源约束；追踪章则必须区分模型实现与仅属语言侧设计的理由，避免虚构模型对应关系。

字段示例：`invariants = "无效计划不得产生 Run；只有阶段列表非空且标识不重复时，构造结果才位于第一个阶段。"`。该示例说明字段应表达的可核查含义，而不是要求所有项目照搬这一对象。

## 结构、设计与证据

本条目保持既定章节、字段键和模型身份，不以论文式章节替代工程责任。目的与边界、声明与契约、行为与约束、追踪与验证、状态与限制分别承担不同论证责任。U 锚点必须显式分配，layer 字段必须与 `docs/design/api/<layer>/<name>.md` 路由一致，源码路径只表示预期映射。

API 验证应覆盖无效输入、输出所有权、错误前置条件、副作用和关键不变量。背景模型和计划用例是评审输入，不是实现证明；实际结果必须绑定具体源码修订和调用记录。

## 视图、来源与限制

本条目不强制图形。若现有 SVG 能澄清 API 所有权或调用关系，可以附加完整六字段图块，但图示不能替代语言级声明或模型实现理由。

来源标识为 DPR；这些标识仅用于追溯写作方法和信息需求，不构成对虚构示例的实现、测试或评审证明。评审应检查声明与文字是否一致、语言侧设计理由是否成立、路由层次是否准确，以及限制是否被表面完整的 API 签名掩盖。
